## 门禁盲区补洞（同日，绿点续）

```

```

**负向验证（两条都必须能红）**：
- contract.mjs 回执帧数 +1 → 2574 vs 2573 → FAIL ✓

## 用 MCP 出片 + 修两个契约缺陷

### 出片（已交付）

`diagram` / `default`：780 帧 / 26s / 1920×1080 / 383193 B / 服务器 13–15s（52–58 fps）。
产物在容器内 `/data/out/`（宿主机 `/opt/cutduo/data/out/`）。

**`downloadUrl` 需要 Bearer token**：`/files/<name>` 不是 nginx 静态目录（配置里没有 files 段），
是 MCP 服务的受保护端点。直接 curl 会拿到 88 字节的 401 JSON，别误判成"文件损坏"。

### 缺陷一：diagram schema 只覆盖 4/17 类 family（已修，v0.3.4）

`params.schema.json` 的 `segments.items.oneOf` 只有 data-bar / data-line / hierarchy / cycle，
而渲染器 `FAMILIES`（`kits/diagram/families.mjs:1721`）有 17 类。后果：`all`(9)、`render-cost`(6)、
`render-cost-20s`(2)、`talkcraft-15s`(5) 四个 preset 在 API 层必被拒，但 CLI 走 `--params` 能出片。
修法：保留原 4 个精细分支，追加兜底分支（family enum + duration）。未知 family 与缺 duration 仍被拒。

**为什么 check 没抓到**：`npm run check` 只 probe 不 validate；`check-kit-contract` 的 `enumOf`
只认 `enum` 数组且正则白名单不含 diagram 的 family 名 → 报"schema 无段型枚举（未对表）"。

### 缺陷二：错误语义错位（已修）

`talkcraft-15s` 用到 timeline + glyph，两类段型的画面完全由字级时刻驱动
（`drawTimeline:1493` / `drawGlyph:1582` 都是硬抛），而仓库里**没有任何 timing.json**。
原来会渲染到一半抛 CapacityError → 回执是 `RENDER_FAILED`。

修法两处：
- `kits/diagram/render.mjs`：缺 timing 时出片前 exit 2，输出 `NEEDS_TIMING` + 具体段落。
  **有意不做假数据兜底**：timeline 是自证图（图上亮到哪儿 == 嘴里说到哪儿），假时间轴等于伪证。
- `api/kits/_runner.mjs`：adapter 之前把非零一律当 RENDER_FAILED；现按入口约定 2 → PARAMS_INVALID。
  这条对**所有 kit** 生效（render.mjs 的 loadParams/auditTiming 都是 exit 2）。

### 仍未解决

`talkcraft-15s` 依然不能出声出片——它需要 5 句配音 + 字级对齐（`docs/字级时间戳-2026-11-15.md` 的
edge-tts + FireRedASR2-CTC 流程）。这是内容决策（要不要为这支元片配音），未擅自做。

## talkcraft 配音（补齐字级时间戳，v0.3.6 待发）

### 链路（全部本机，不上传）

```bash
node kits/diagram/tools/vo.mjs --params <preset> --out-params out/x.vo.json --out-audio out/x.vo.wav
```

- 实测 total 20.14s，match 1.00 / 0.615 / 1.00 / 0.692 / 1.00

### 低 match 不等于锚点错

第 2/4 句识别成「配音先**去橙次**」「屏幕上的**树**…这一**针**的**针执**」，match 0.62/0.69。
核对后仍可用：5 段字刻线**全部单调递增**、字字有时刻、最大间隔 0.52s、跨度与 speech 吻合。
**对齐看位置不看读音** —— 这正是文档说的同音字不算错。

相对仓库根的写法在 cwd≠仓库根时解析失败。改成走 `resolveInput` + 缺文件 exit 2。

## MCP 异步降级实测（2026-11-16）

阈值是 `MAX_WAIT_SECONDS=90`（compose 里 `CUTDUO_WAIT_SECONDS: "90"`）。
`doRender` 的循环每 400ms 查一次 jobStatus，超时就返回：

```json
{"pending":true,"jobId":"job-…","status":"running","queuePosition":null,
 "note":"超过 90s 未完成，用 cutduo_job_status 轮询"}
```

两条路径都实测过：

| 场景 | 任务 | 耗时 | 返回 |
|---|---|---|---|
| ≤90s | desk/hotpot 3420 帧 | 87.56s | 直接 `output` + `downloadUrl`（也带 jobId 供对账） |
| >90s | desk/nanjing 4380 帧 | 120.16s | 先 `pending`，轮询 1 次仍 running(115.3s)，2 次 done(120.2s) |

**幂等**：done 后重复 `job_status` 返回完全一致的回执（含固定的 elapsedSeconds/finishedAt）。

### 给调用方的结论

1. **不能假设一次调用就拿到产物**。必须处理 `pending` 分支。
2. hotpot 87.56s 距阈值只差 2.44s —— 边界很窄，同一支片换个负载就可能降级。
3. 轮询间隔不必太密：400ms（服务端自己的节奏）合理；客户端 2–3s 足够，一个 120s 的任务也就 40–60 次请求。
4. `pending` 时 `queuePosition` 为 null 是因为任务已在 running，不是排队——别拿它判断进度。

### 顺带的性能观察

同机同 kit，3420 帧 87.56s（39.1 fps）vs 4380 帧 119.91s（36.5 fps）。
**fps 下降反而符合预期**：片更长，启动开销摊得更薄，但对 60fps 大画幅来说，瓶颈是每帧的像素填充与照片合成，不随片长改善。
