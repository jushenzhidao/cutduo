## 12:26–12:41 · 「CanvasKit SkSL 优化视频」：先量瓶颈，再用数据否决

**结论**：本机 Node 无 GPU，CanvasKit 走 CPU raster，SkSL 1440×1080 单帧 **867ms**（零拷贝 raw）/
1172ms（PNG），是现有链路 34.4ms 的 **25.2×**。而瓶颈根本不在绘制：draw 1.52ms（4.4%）/
JPEG 28–33ms（**95.6%**）。SkSL 的理论天花板只有 4.4%。

- 编码通路：jpeg q94/q80/q60 耗时几乎相同（28–33ms）⇒ 降质量只省体积（292→66KB/帧），不提速；
  webp 125–151ms、png 326ms 更慢；raw `getImageData` 23.6ms，但每帧 6MB（20×）。
- 端到端：rawvideo 比 JPEG 快 **1.18×**，代价管道数据 **19.8×**（240 帧 1.42GB）。
- **CanvasKit 0.42 的坑**：CPU surface 只能 PNG（`encodeToBytes` 对 JPEG/WEBP 返回 null）；
  uniform 必须**严格 3 floats**（u_time 1 + u_res 2），多传 1 个 → `makeShader` 返回 null →
  整条片 4.1KB 全黑，而脚本仍打印「uniform OK」。已加双断言：shader 非空 + 首帧 R 通道极差 ≥20。
- 能力验证：SkSL 3s / 720×540 / 72 帧 / 53.4s（1.3 fps），画面正常（渐变光带 + 12 翻牌格 + 噪点 + 字幕条）。
- 与并行任务 PLAYBOOK §45.1–45.5（skia-kit 纯色）数字差 2–4×：绘制 0.5% vs 4.4%、JPEG 7–15 vs 28–33ms
  ⇒ 内容复杂度（噪点让 DCT 更贵）会翻转 raw/JPEG 的相对收益；结论一致：SkSL 不适合 Node 批量出片。

## 12:44–12:55 · 按《CanvasKit SkSL Motion 蒸馏方案》逐条实测：**修正上一轮结论**

用户给方案文档要求「用这几种方案试试」。文档核心判断「GPU 蒸公式 / CPU 蒸结果」在本机成立，

| Lottie | ? | 无 AE 产物，未验证 |
