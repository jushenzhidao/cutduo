## 00:56 · 评估「能不能用 Rust 加速」

**结论：已经在用，剩余空间 ≤10%。**

- `@napi-rs/canvas` 1.1.0 的原生模块 `skia.darwin-arm64.node`（28MB）就是 Rust（napi-rs + skia-safe），
  绘制层每帧都在跑 Rust。
- 实测单帧分解（1440×1080，`bench/enc-probe.mjs`）：
  绘制 **0.95ms** / 取帧 RGBA 6MB **0.85–1.21ms** / x264 veryfast crf20 **6.10ms（75%）**。
- 编码是瓶颈，而 x264 是 C + 手写 SIMD；Rust 重写编码器只会更慢（rav1e 比 x264 慢一个数量级）。
- Rust 唯一有意义的落点：取帧零拷贝直送 libx264，省 1.2ms ≈ 10%，但要自建 FFI 调度。

**两个反直觉实测（推翻假设）**：
1. `-threads 1` 更慢（6.95 vs 6.10ms）⇒ 不存在「8 进程 × 多线程过度订阅」问题。
2. `videotoolbox` 单进程更慢 27%（h264 7.77 / hevc 7.82ms）⇒ 硬件编码的固定开销在这里吃掉优势。
   但**它不占 CPU**，8 并发时可能反超——唯一未验证的 2× 路径，需单独测。

**另一处必须记的测量教训**：探针第一次测出「取帧 28.45ms」，是未预热 + 连续分配 6MB 触发 GC
的假象；预热后是 0.85ms，差 33 倍。**任何取帧/编码探针，先预热 5 次再计时。**

## 04:40 · 整体架构改为 agent api first（提交 `7404726`）

**一句话：API 是唯一实现，CLI 是它的宿主。** `kits/` 仍是实现层，但对外只暴露 `api/`。

### 结构

```
api/index.mjs     唯一业务实现，导出六个动词
api/cli.mjs       宿主 1：命令行（--json / --stdin 做 JSON in/out）
api/contract.mjs  请求规范化 + 回执构造
api/errors.mjs    ApiError(code/message/hint/fix/details)
api/validate.mjs  手写 JSON Schema 校验器（不引 ajv：五支方言混用，用到的关键字只有十来个）
api/registry.mjs  五支注册 + 别名（desktop→desk、sci→science）
api/kits/*.mjs    五支 adapter，共用 _runner.mjs
api/capabilities.json  由代码生成，删掉 repoRoot 后入库
```

动词：`capabilities / describe / validate / render / probe / gate`。
`validate` **永不抛**（语义就是「告诉我哪里有问题」），其余抛 ApiError。

### 三条定死的设计决策

1. **回执只信探测**：帧数/时长/分辨率一律 ffprobe 读产物。各 kit 打印的是「2573 帧计划」，
   是计划值不是实际值；五支自述格式还各不相同，解析 stdout 会让实现差异泄漏进契约。
2. **错误必须可纠正**：`code` 可分支、`hint` 说原因、`fix` 给可执行动作。
   `validate` 报错精确到 JSON Pointer（`/scenes`、`/scenes/0/dur`）。
3. **overrides 白名单只放渲染超参**（fps/workers/crf/preset/pipe/at/theme/transition），
   内容必须走 `params`；混用会让回执里的 `request` 无法重放。白名单硬编码在 `contract.mjs`。

## 04:45 · 第二轮：异步 job + 补齐 schema（提交 `3e07544`）

### job 模型（`api/jobs.mjs`）

`submitJob / jobStatus / listJobs / cancelJob`，CLI 对应 `render --async` / `status --id` / `jobs` / `cancel --id`。
状态机 `queued → running → done|failed|cancelled`，状态只落 `out/jobs/<id>.json`，跨进程可查。

**三个必须记住的实现约束（都踩过）**：

1. **一 job 一独立进程**（`detached + unref`）。API 进程先退出时任务要继续跑，worker 线程做不到。
2. **判定终态以产物为准，不以 pid 为准**。系统复用 pid，`kill(pid,0)` 成功不代表还是那个 job。
   第一版只看 pid，结果已完成的 job 被永久卡在 `running`——**比报错更糟，调用方会一直等**。
   现在先读 stdout，有完整 JSON 就判终态。
3. **`elapsedSeconds` 取 stdout 的 mtime**，不是判定时刻。否则同一个 job 在不同时间查询会得到
   不同耗时（第一版就出现过 10.9s vs 实际 5.15s）。回执必须可重复。

还有个过滤 bug：`<id>.stdout.json` 后缀同样是 `.json`，被 `list()` 当成 job 文件读入，
shape 出 `undefined`。改用正则 `/^job-\d{8}-\d{6}-[a-z0-9]+\.json$/`。

## 04:44 · 第三轮：job 并发上限（排队，不拒绝）

`MAX_JOBS = clamp(1..4, cpus/8)`，30 核机器上 = 3，可用 `CUTDUO_MAX_JOBS` 覆盖。
上限通过 `capabilities().limits` 对外公开，`status` 返回 `queuePosition`。

**核心决定：排队，不拒绝。** 超出上限的任务停在 `queued`，不报错。理由是每个渲染本身已经
8 worker，多开只会互相拖慢；拒绝会让调用方自己实现重试与退避，那是把复杂度推给使用者。

**代价必须记住：`status()` 不是纯查询。** 没有常驻调度器，补位发生在 `submit / status / list`
调用时（lazy scheduling）。`status()` 会读全部 job 文件、reconcile 已死的 running、拉起队首。
所以：
- 它能顺带实现自愈（已死但状态没更新的 job 会被判终态，释放槽位）；
- 但任何「只是看一眼」的调用都可能启动一个新任务，写测试时要注意。

**实测：吞吐 1.6× 提升，单任务延迟 +70%（更正：初版我写成「几乎无吞吐收益」，错了）。**
5 个 mg：3 并发时单任务 12.0 / 12.5 / 11.9s，补位两个各 9.4 / 9.5s，**总墙钟约 22s**；
串行单任务 7s、总墙钟约 35s。所以并发的收益是吞吐（0.23 vs 0.14 job/s），
代价是单任务延迟 +70%。上限的意义是防止十个任务抢到全部超时，不是提速。
初版错误来自只看单任务 12s vs 7s 就下结论，没算总墙钟。

取消分两种：`queued` 直接出队（0.2s，不 spawn）；`running` 先 SIGTERM 给 2s 收尾再 SIGKILL，
并在取消后立刻 `schedule()` 补位（取消常发生在长任务上，不补位会白等）。

### 架构

`mcp/server.mjs`，零依赖（`node:http`），JSON-RPC over `POST /mcp`，无状态、不要求 session id。

| 路由 | 用途 |
|---|---|

| `POST /assets` | 二进制上传（MCP 工具参数是 JSON，塞不进几 MB 音频） |
| `GET /files/<name>` | 产物与资产下载 |
| `GET /health` | 存活探测，免鉴权 |

1. **容器里没有 `.git`**，`src/root.mjs` 向上探测会走到 `/` 然后退回 `src/`，路径全错。

2. **上传不能 `req.pipe(ws)`**：超限时 `ws` 的 `'finish'` 永不触发，请求挂到 nginx 504，
   客户端拿不到 413 的真实原因。改成手动 `for await` + 逐块判大小。
3. **`playwright` 移出 dependencies** 到 devDependencies。云端不出 `.motion` 模板，

## 05:2x · 画幅参数化：竖屏模板曾被渲成横屏

**根因**：`render.mjs` 里 `1920×1080` 写死 5 处（两处 `createCanvas`、`createScienceRenderer`
的 width/height、`createWebCanvasRenderer` 的 width/height、ffmpeg 的 `-s 1920x1080`）。
`--kit <模板名>` 虽然有 manifest 可读，但从来没读过 —— 竖屏模板会被静默渲成横屏。

**改法**：
- `kitSpec()` 读模板 `motion.json` 的 `output.width/height`，带进 spec
- 主线程算 `OUT_W = P.width || SPEC.width || 1920`（内容 > 模板声明 > 默认）
- worker / probe / ffmpeg 全部用这个值，不再有字面量
- 竖屏实测：1080×1920 ✓；横屏回归：1920×1080 ✓

**顺带发现第二个错位**：`subtitle.y: 980` 是横屏绝对像素，竖屏下字幕跑到画面中部、
压住了副题。改法：`y ≤ 1` 视为相对高度，`> 1` 视为绝对像素（旧 preset 兼容）。
骨架 preset 改成 `0.907`，跨画幅天然安全。

**新增门禁**：`output` 的宽高比必须等于 `guide.layout.ratio`，否则 FAIL。
防的是「声明 16:9、实际输出 1080×1920」这种自相矛盾——字幕与安全区会整片错位。

**教训**：画幅这类"到处都用到"的量，只要有一处写死，声明就会变成装饰。
判别方法不是读代码，而是**把声明改成另一个值，看输出跟不跟**。

## 09:4x · clay 配音：`duration` 是硬约束，段长不能小于 9

1. **70s 被压成 26.78s**：一句旁白只有 2.6–3.0s，`vo.py` 默认段下限 2.6 会把段压到 3–4s。

3. **段长 < 9 时动画跑不满**：duration 被 clamp 到 9、段长 8，动画只播到 89%，最后一块没落位。

3. **本影填充 alpha 0.9 会让球只剩一团棕**（轮廓消失）；0.55 + 红色边界线才读得出「影扫过球面」。

### 生成式素材规范（10:50，`docs/ASSET-POLICY.md`）

用户问 BGM / TTS / 生图 / 动图 / 视频 / 数字人「什么场景触发、能不能成规范」。

理由是可复现——渲染期调 API 会让逐帧一致、多 worker 分片、离线重跑、两版 diff 全失效。

**判定顺序（按信息缺口，不按审美）**：先问「这段要传达什么」→ 版式能不能承载（能就不生）

数字人单段 ≤30s、四项验收（口型/眨眼/手指/牙齿）崩一项就换 TTS+头像。

**三条红线**：① 渲染期不调生成 API；② 无 `source` 不进口；③ 生成素材不承载关键信息。
软约束：`generated` 素材 ≤ 总镜头 1/3。

**冻结记录**要求 `source.type` 四态（generated / synthesized / shot / stock）+ prompt/model/seed

## 11:2x · 加 BGM（用户：可以加点 bgm 吗）

仓里**没有任何曲库**（`assets/audio/*.m4a` 全是配音），外地网络（Openverse/Pixabay）**curl 超时**。

### 新工具 `tools/add-bgm.mjs`
`--video --loop "<名字>"|--music <路径> --out`，默认 gain −15dB / duck on。

### 四个必须踩过的坑（都实测过）
1. **不能用 `-stream_loop`**：首尾硬接，每 8.3s 一个断口，人声片上一听就是"啪"。
   改成 N 份拷贝逐段 `acrossfade=1s`（拼接总长 `N*L-(N-1)*d`）。
2. **不能用单趟 `loudnorm`**：它是动态增益，段与段电平被来回拉；实测加 BGM 后同一秒反而**低 2.8dB**。
   改固定增益 + `alimiter=limit=0.9:level=0`。**`level=0` 必须写**——默认 level=1 会自动归一化，又吃掉 1.6dB。
3. **声道必须跟随成片**：vo.py 出的是**单声道**，链里写 `channel_layouts=stereo` 会让人声每声道 −3dB，
   表现为"加了音乐反而变小"。统一 mono，输出 `-ac 1`。
4. **duck 参数别过**：初版 thr 0.02/ratio 10 等于全程重压，BGM 实际听不见。
   现用 thr 0.125(−18dBFS)/ratio 2.5/release 450。

### 实测（女声版）
空隙 −31.0dB（原片 −77dB 纯静音）、说话段 −18.1dB（原片 −18.4，人声基本不动）、
积分响度两版都 −15.9 LUFS、门禁 PASS。最大采样跳变 17169 vs 原片 17170（在人声 70.08s 处，不是接缝）。

### 授权
Apple Loops 允许用在作品里，**不允许再分发循环素材** ⇒ .caf 不进仓库，工具里只记名字与路径；
成片里混好的音轨随成片走。
