## 00:55 · 栈名定为「Skia 直出」

用户问「这个技术栈应该叫啥 速度很快？」。答：叫 **Skia 直出**，不用「快」命名。
- 「直出」两个含义各对应一个快因：直出编码器（绕过浏览器，6×）、直出裸帧（不做中间 JPEG，10–30%）。
- 相对实时 5.7×（68.8s 片 11.98s）；Chromium 0.9×（75s）、cinecode 0.4×（168s）。
- 诚实边界：放弃 HTML/CSS 通用性；裸帧 8.8GB 过内存只在本地成立；GPU 壁纸依赖 headless-gl。

## 00:56 · 评估「能不能用 Rust 加速」

**结论：已经在用，剩余空间 ≤10%。**

- `@napi-rs/canvas` 1.1.0 的原生模块 `skia.darwin-arm64.node`（28MB）就是 Rust（napi-rs + skia-safe），
  绘制层每帧都在跑 Rust。
- 实测单帧分解（1440×1080，`bench/enc-probe.mjs`）：
  绘制 **0.95ms** / 取帧 RGBA 6MB **0.85–1.21ms** / x264 veryfast crf20 **6.10ms（75%）**。
- 编码是瓶颈，而 x264 是 C + 手写 SIMD；Rust 重写编码器只会更慢（rav1e 比 x264 慢一个数量级）。
- Rust 唯一有意义的落点：取帧零拷贝直送 libx264，省 1.2ms ≈ 10%，但要自建 FFI 调度。

**两个反直觉实测（推翻假设）**：
1. `-threads 1` 更慢（6.95 vs 6.10ms）⇒ 不存在「8 进程 × 多线程过度订阅」问题。
2. `videotoolbox` 单进程更慢 27%（h264 7.77 / hevc 7.82ms）⇒ 硬件编码的固定开销在这里吃掉优势。
   但**它不占 CPU**，8 并发时可能反超——唯一未验证的 2× 路径，需单独测。

**另一处必须记的测量教训**：探针第一次测出「取帧 28.45ms」，是未预热 + 连续分配 6MB 触发 GC
的假象；预热后是 0.85ms，差 33 倍。**任何取帧/编码探针，先预热 5 次再计时。**

## 01:00 · 编码器与并行度对比实验（用户要优化方案）

同片同配置只换一个变量，4127 帧 / 1440×1080@60 / GPU 壁纸 / 裸帧，30 逻辑核（10P+20E）。

**① 编码器：速度没差，体积差 5.7–7.6 倍**
| 编码器 | 吞吐 | 体积 |
|---|---|---|
| x264 veryfast crf20 | 417 fps | 6.63MB |
| h264_videotoolbox 6M | 420 fps | 50.12MB |
| hevc_videotoolbox 4M | 424 fps | 37.93MB |
等码率（1M）再验：vt 实际 1.6Mbps/4.0MB vs x264 0.68Mbps/1.7MB，仍差 2.4×。
⇒ **硬件编码三点全输**，之前「并发下可能反超」的假设被推翻。

**② worker 扩展性：8 已饱和**
8 → 16.85ms/帧；12 → 20.21；16 → 25.88。壁纸层同时 2.28→2.58→2.92ms
（多 GL 上下文争抢）+ 8 个 ffmpeg 分片 I/O 竞争。30 核里 22 核空闲也不涨。

**③ `-tune animation`：唯一免费收益**
体积 1.70 → 1.30MB（−24%），单帧 16.38 → 16.84ms（+3%），字幕区 SSIM 0.9915，
4× 放大无可辨退化。原因：本仓模板全是平涂色块+文字，正好是该 tune 的目标内容。

**结论**：1440×1080@60 下已达架构极限（8.5× 实时）。再快只能改内容规格（30fps / 1280×960），
不是改代码。Rust 重写 ≤5%，硬件编码 0。

## 01:05 · 超参预设（--profile）落地

用户要「设置超参灵活选择」。做成**两层**：`desktop-kit/profiles.json` 预设 + CLI 单项覆盖，
优先级 CLI > profile > 默认，运行时打印生效配置。

5 档（1200 帧 / 20s 实测）：

| 档 | 编码 | 单帧 | 体积 |
|---|---|---|---|
| `standard` ★ | x264 vf crf20 + animation | 16.4ms | 1.38MB |
| `small` | x264 vf crf25 + animation | 16.4ms | 0.83MB |
| `archive` | x264 slower crf17 + animation | 25.0ms | 2.50MB |
| `tiny` | x265 vf crf30 + hvc1 | 23.3ms | 0.72MB |
| `flat` | static + x264 vf crf20 | 27.0ms | 2.05MB |

完整片 standard：**4.72MB / 9.71s / 424.9fps**（未开 tune 是 6.63MB，-29%）。

**三条被实测推翻的设计**：
1. **删掉了 `speed` 档**：ultrafast crf23 只快 2.7%（15.92 vs 16.36ms），体积却 2.5×
   （3.3 vs 1.38MB）；CRF 提到 28 仍 1.8MB 不划算。⇒ **不存在比 standard 更快的档**。
2. **`flat` 比 GPU 版慢 65%**（27.0 vs 16.4ms），原因不是缺 GPU，而是内置静态壁纸的**固定噪点
   让编码更难**（传帧 24.62 vs 12.45ms）。低频流体壁纸反而好压——这同时解释了 GPU 版体积更小。
3. **HEVC 必须重打 `hvc1`**：分片 mpegts 的 tag 在 concat -c copy 后丢成 `hev1`，Safari 不认。
   在最终封装补 `-tag:v hvc1`，实测 `codec_tag_string=hvc1`。

冒烟：默认档正确、未知档报错并列出可选、`--crf 22` 覆盖 small 的 25、verify 13/13。

## 01:48 · PoC 验证：.motion 模板换宿主跑 Skia（成功）

**三个障碍与解法**：
1. `data/film.js` 缺（宿主生成）——PoC 手写最小 FILM；整片需按 instance/film.json 生成

**参数坑**：每镜 props 契约不同，用错只画窗口壳。应用 `meta.props` 默认 ← `meta.example.props`。
