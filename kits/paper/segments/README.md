# paper 段型卡

> 每个段型一张卡。**给写新片的人看的**，不是给改渲染器的人看的。

## 为什么单独拆出来

`kits/paper/README.md` 里有 8 个段型的一行说明（"args 是什么"），`MEMORY.md` §六 里有零散的坑（"例外点必须跳出网格"）。写新片时要同时翻两处，而改渲染器的人才需要看 `paper.mjs`。

这三类读者混在一起的结果是：**参数表缺失**（只有字段名，没有"改这个数会发生什么"），**坑记在别处**（改代码时根本不会去看 MEMORY）。

卡格式照抄 `video-shotcraft` 的 124 张镜头配方卡——它的价值不在内容，在**结构**：`意图 → 选型 → 参数表（典型值 + 调节手感）→ 已知坑 → 参考实现`。

## 卡格式

```markdown
---
name: <段型名>
一句话: <它到底解决什么问题>
适用: <什么内容该用它>
时长: <典型秒数>
能量: 高/中/低
标签: <分类>
---

## args          —— 字段表，只写类型与含义
## 意图          —— 为什么需要这个段型，它在叙事里承担什么
## 参数表        —— 三列：参数 / 典型值 / **调节手感**
## 已知坑        —— 踩过的、不写下来就会再踩一次的
## 动效          —— 时间顺序，不写缓动函数名
## 参考实现      —— 代码在哪
```

**参数表的第三列是重点。** 不是"取值范围 0.5–2.0"，而是"0.5 = 读作闪现，2.0 = 观众开始等"。前者是文档，后者是经验。

## 节奏门槛（2026-11-14 实测，可直接算）

`tools/pacing.mjs` 判「静止」的口径是：**320×180 灰度、0.1s 间隔、均值差 < 0.35**。
下面六条是从 `birthday-paradox` 的 6/9 → 0/9 里测出来的，设计长段（>8s）时先按这个算一遍。

| # | 结论 | 数值 / 算法 |
|---|---|---|
| 1 | 一次揭示要被识别 | 约 **153 个变化像素**（`0.35 × 57600 / 灰度差 100`） |
| 2 | **时间窗口会摊薄幅度** | 0.4s 的弹出每 0.1s 只完成 25% ⇒ 均值差 **0.10**（门槛 0.35） |
| 3 | 有效窗口 | **0.1 – 0.26s** |
| 4 | 有效位移 | **40 – 90px**（90px 才压得住 42px 的小字） |
| 5 | 遮罩扫出**反而更差** | 同一时刻只露 1/3，实测均值差 0.163 |
| 6 | 事件数需求 | ≥ **段长 ÷ 8**（12s 的段至少 2 个事件，且要分布开） |

**怎么用第 1 条**：把元素的宽高换算到 320 宽（除以 6），面积 × 灰度差 ÷ 57600 = 均值差。
- 一行 38px 字（8 字）≈ 40×6 = 240px²，灰度差 100 → 均值 0.42（刚过）
- 一行 42px 的 sub（8 字）≈ 392px²，但浅灰字灰度差只有 25 → 均值 **0.17**（**不过**）
  ⇒ 所以 number 的 sub 必须加上滑位移，光靠"出现"不够。

**怎么用第 6 条**：数一下这一段有几个「可以被看见的时刻」。
- `compare` 4 条正文 → 够
- `steps` 5 步 → 够
- `hero` 2 行 → **不够**（12.4s 需要 2 个且必须分布在 0.7 / 10.5，不是 0.7 / 3.4）
- `number` 1 个环 + 1 个数 → **不够**（把 sub 拆三段补上）
- `outro` 1 个 CTA → **不够**（把 title / sub / CTA 推到 0.05 / 2.5 / 6.5）

**做不到怎么办**：只能加内容（新的行、新的条目）或拆段。渲染器侧的手段（缓慢运镜、加大缩放）
在 0.1s 采样下每帧位移不足 1px，砸不穿阈值 —— `drift z=1.08` 在 18.6s 的段上只带来 2.75s 改善。

## 可信度标注（重要）

卡片里「参数表」的第三列分两种来源，**读的时候要分清**：

| 来源 | 长什么样 | 可信度 |
|---|---|---|
| **实测** | 有具体事故现场、有数字 | 高。这些都是真出过问题、写进 MEMORY 的 |
| **算术** | "N 个 × 0.008 = 0.8s 铺满" | 中。算式对，但"读起来什么感觉"没验过 |
| **推断** | "读作一闪""观众会开始等" | 低。**这是我的外推，不是看片得出的** |

**有实测支撑的结论（可以直接信）：**

| 卡 | 结论 | 现场 |
|---|---|---|
| `chart` | freezedetect 会把该段误判成冻结 | 标记点占 0.02%，低于 0.2% 阈值 |
| `checklist` | 大数字改回总数会让整段被判 12.5s 冻结 | 实测 12.5s |
| `steps` | 逐卡 fitSize 会让基线错位 | 3 字 44px / 4 字 38px，各卡按自身 inkAsc 对齐 |
| `steps` | 卡片左对齐硬排会在 N=3 时错位约 200px | 只有 N=5 时碰巧与节点重合 |
| `grid` | 例外点换色、换方形都分不出来 | 两种都试过，9px 尺度下无效 |
| `number` | `from=0` 会把中间值当事实上屏 | 标签是"误差上限"而中间值 1%、2% 清晰可见 |
| `hero` | 入场时刻早于段起点会整体平移 | `shift` 逻辑，写小于 t0 的值不报错 |
| `broll` | 纯纸信息量 0–1.5，会被判空镜 | 引文 18–20 / 图文 56 |

**其余「读作…」「观众会…」的判断，都没有实测。** 它们是从版面几何和时长算出来的合理外推，
第一次真用某张卡时，如果和描述不符，**以实测为准并回来改这张卡**。

## 写作原则

1. **只写实现里能验证的事。** 参数默认值去 `paper.mjs` 读，不要凭印象写（本文档已出现过"README 说 8 个版式、代码里 11 个"这类偏差）。
2. **坑必须有现场。** 写"曾经出过什么问题"，不写"注意不要出错"。
3. **参数表要给因果。** 改大改小分别会发生什么，一句话说清。
4. **不重复 README。** 入口、CLI、tokens 这些在 `../README.md`；这里只讲段型本身。
