# 七个开源「代码渲染视频」Skill：可吸收性评估

> 评估对象：微信公众号《不用任何视频模型！这 7 个开源 Skill 做视频，全靠写代码一帧帧渲染》（晓白AI纪元，2026-10-31）
> 评估基准：本仓（cutduo / Skia 直出 + 参数化段型 + 时间轴契约 + 六动词 API + 六项门禁）
> 评估口径：不看 star、不看宣传，只看「是否命中本仓已记录的缺陷」与「能否在纯函数 t→帧 模型下工作」

## 二、A 级：三项直接吸收（止血项）

### A1. 关键词锚点 `marks`：把「手写秒数」换成「说到某个词」

**本仓的病**：`MEMORY.md` §五 是全档最长的一节，几乎全部同源——内容侧手写绝对秒数/段内相对秒数，写错就静默失败：

- 卡片 `at: 71.72` 远超段末 → 卡片永不出现 → 画面只剩字幕（实测 40–43s 空镜）
- `screens` 元素钉在 4.2s 而子段只有 3.6s → 永不出现 → 只剩标题
- `number` 段不给 `dur` → 数字瞬间到位、后面整段静止

这些都是**同一个根因**：时间由人算，算错不报错。

**对方的解**（dashi `pipeline/生成timeline.mjs`）：内容侧不写秒数，写词。

```json
{ "marks": [ { "name": "幸存者偏差", "phrase": "幸存者偏差", "cue": 3 } ] }
```

生成时在**字级时间轴**（`subs.chars`）里按短语查找，取首字起点与末字终点：

```js
TL.mark('词')      // 说到这个词的时刻
TL.markEnd('词')   // 说完这个词的时刻
TL.has('词')       // 不确定时先查，避免抛错
```

页面侧铁律写进 SKILL.md：**「时间一律从 TL 取，不写死秒数」**。找不到词直接报错，并告诉你"在第几条字幕里找的"。

**关键判断：本仓不需要 whisper 也能落地。** dashi 有 `--no-whisper` 降级路径：静音检测找句界 + 句内按字数摊，实测**字级平均差 0.08s、最差 0.45s**。本仓字幕本来就按字数与配音同步，这套近似是现成的。±0.45s 对"卡片何时出现"完全够用——比"永不出现"好一个数量级。

**落点**：`src/temporal.mjs` 增加 `resolveMarks(params, wordTimes)`；`at` 字段允许 `{ "$mark": "词" }`；`new-film` 生成时把关键词写进 screens；build 时对无法解析的 mark **抛错而非警告**（现在的 clampTimes 是静默压缩，属于同类的"猜"）。
**改动面**：`src/temporal.mjs` + `tools/new-film.mjs` + schema 放行 `$mark`。纯增量，不动渲染器。

### A2. 确定性检查：同一 t 渲两次，必须逐像素相同

**本仓的病**：零覆盖。`src/verify.mjs` 是坐标断言（`hero 标题 at 2.5 → x:144`），不是状态泄漏检查。`gate.mjs` 六项全是成片指标，也不查这个。

而本仓的渲染模型**必然**存在这个风险：Skia 侧 `ctx` 跨帧复用，`renderFrame(t)` 只重画不重置。任何一处漏写 `ctx.globalAlpha = 1` / `setLineDash([])` / `lineJoin`，状态就会漏到下一帧。

**对方的解**（dashi `render.mjs --check-determinism`）：

> 每个时刻在新打开的页面里单独截一张，再先跳到片尾附近、倒回来截一张，比两张是否逐像素相同。不同 = 画面跟 seek 的先后有关（常见原因：画布的 lineCap、lineJoin、setLineDash、globalAlpha 等状态没复位，漏到了下一帧），**按时间顺序出片时不一定看得出**。

且明确记录了受害名单：「v1.3 前立体卡通、黑底科技、复古报刊的示例页都踩过」。这不是理论风险。

**落点**：`tools/determinism.mjs`，Skia 版等价实现：

```
t ∈ {0.25L, 0.5L, 0.75L}
imgA = snapshot(t)
renderFrame(远处 t2);  renderFrame(t)
imgB = snapshot(t)
assert pixelEqual(imgA, imgB)
```

**成本极低**：不渲染视频，只需 6 次 `renderFrame` + 2 次 `getImageData`。可以挂进 `npm run gate` 作为第 7 项，也可以挂在 `smoke.sh`。

### A3. 两张人眼复核拼图：扫片 + 卡点

**本仓的病**：门禁是数字指标，抓得到"空帧率 8%"，抓不到"标题被截断"、"两个字叠在一起"、"关键词卡比口播早 0.4 秒"。而这三类恰好是最常见的交付事故。

**对方的解**（dashi `--scan` / `--check-marks`，都不出片）：

| 工具 | 做法 | 看什么 |
|---|---|---|
| `--scan` | 每秒 3 帧，每格 480×270，一张 4×8 格（约 10.7s） | 截断、叠字、闪烁、空白、字幕是否跟着换；**镜头交界前后 0.5s 最容易出事** |
| `--check-marks` | 每个关键词开始**前 0.1s**、**后 0.35s** 各一帧，一行两个词 | 「前」还没有动作、「后」已开始出现 = 卡上了 |

**落点**：`tools/contact-sheet.mjs`（纯 ffmpeg，一条 tile filter，约 10 行）。
注意 `--check-marks` 与本仓 A1 天然咬合：有了 `marks` 才有"关键词前后帧"可取。

### A4（附）. 静帧取时刻必须给逐字浮现留余量

**本仓已有的正确判断**：`publish-pack` 封面取**段末**不取段中（元素逐个长出来，取中点只有一半）。

**对方补的一条更细的**：手写/逐字浮现类风格，要取「关键词开始说之后约 **0.3 秒**」——「实测 4.95 秒只写出『失』，5.15 秒才是『失忆』」。

**落点**：`publish-pack` 的取帧逻辑，对 `sketchnote` / `chalkboard` / 手写类段型加 +0.3s 偏置。一行改动。

## 三、B 级：要改造，但命中真实缺口

### B1. 运镜层：本仓唯一的结构性视觉缺口

**本仓的病**：`paper` / `science` 全是固定机位 + 元素自己生长。短片段看不出问题，**长片（90s+）会读成 PPT**。这不是审美问题，是结构问题：画面里没有"摄像机"这个维度，所有变化都发生在同一张平面内。

**对方给的东西最完整**（huashu `references/镜头语言.md` + `lib/camera.js`）：不只是"加个 zoom"，而是一张**带反面标尺的参数表**：

| 动作 | 参考数 | 什么时候不用管 |
|---|---|---|
| 停 | 按口播，无上下限 | 观众在读字、画面自己在动 |
| 缓推 | 0.6–1.5s，sineInOut，推近 10–40% | 推的距离 >2 倍时可到 2s |
| 拉远 | 0.8–2s，起步快、长尾落定 | — |
| 横移 | 0.5–0.9s；沿红线追 1.3–1.8s | 跟随运动物体时速度跟物体 |
| 快推 | 0.25–0.35s 推近 18–32% | 只在揭晓/反转/关键数字 |
| 砸入 | 0.17s，1.55→0.94→1.0 | 一镜最多一次 |
| 慢漂 | 1–4%/s | **解说片里每镜都慢推就是 PPT** |

**反面标尺（这是最有价值的部分）**：某支 102 秒、44 镜的片子，代码里推近约 48 次（平均 2.1 秒一次），全是往里推、几乎没有拉远和横移。作者原话：「次数太多，而且节奏太快了，一点都不 smooth」。门禁量到推近每分钟约 12 次（这是下限）。

还有一条可直接做成 lint 的判据：**重音动作（快推+砸入+甩）占镜头数 ≤ 1/3；不连着三镜往里推；推近次数 > 8 次/分钟 报黄。**

**与本仓的兼容性判断**：`paper` 的段型是"元素生长"式，本身已有运动。huashu 的规则里正好有对应的一条——「画面自己在动，就更不用动镜头，镜头一动反而抢戏」。所以运镜层应当是**段级的、可关闭的**，不是全局默认。

**落点**：
1. `src/pipeline.mjs` 的渲染循环外包一层 `ctx.save() → ctx.translate/scale → 段渲染 → ctx.restore()`；
2. `scenes[i].args.camera` 支持 `{kind:'push'|'pull'|'punch'|'cut', dur, z}`，缺省 `cut`（即现状，零回归）；
3. `src/gate.mjs` 加一项「推近次数/分钟」只报不拦（与本仓"三项连续分布指标只报不拦"的既有结论一致）。

**成本**：改动面集中在 pipeline + 一个 `src/camera.mjs`，段型一个都不用改。这是 B 级里性价比最高的一项。

### B2. 代码合成配乐：解决"配乐不入库"的结构性脆弱

**本仓的病**（`tools/audio-bed.mjs` 文件头自述）：

> 曲目路径是本机资源（`/Library/Audio/Apple Loops/Apple`），**不入库**；找不到就报错并列出可用曲风，不静默降级成"没配乐"。

实测本仓 `assets/` 下 loop 文件数 **0**。也就是说：**换一台机器（或进 CI）就出不了带配乐的片**，而且每换一种曲风都要手工调 `TRIM` 线性补偿（hiphop 要 2.6 倍，因为 Afloat 比 electrohouse 低 9–13 dB）。

**对方的能力**（mg-styles-15 `lib/audio/mgaudio/`，13 个 py + 6 个 recipe）：

- 48kHz float stereo，numpy + numba，band-limited PolyBLEP 振荡器、TPT ladder/SVF 滤波、Karplus-Strong、FM
- **完全确定性**（seeded），10s 混音 3–8 秒渲完
- 输出严格 10.000s、−14 LUFS、真峰值 ≤ −1.1 dBTP
- 6 类 recipe：chill / club / fun / retro / world + synthwave / darksynth / vaporwave / chiptune / techno / acid / pop / future_bass / trap / glitch_hop / lofi / ambient / guofeng / variety / explainer（共 19 种，按风格名映射）
- 有一整套 SFX 家族：whoosh / riser / impact / pop / blip / click / paper / stamp / pen / shutter / typewriter / glitch / stutter
- 三个**架构级约定**值得抄：
  1. `Sound = buffer + sync point`。**whoosh 同步在"掠过峰值"、riser 同步在"末端那一击"**，调用时传视觉事件时间，不传缓冲起点。这一条消掉了"音效早 0.3 秒"的整类 bug。
  2. `music`（−20 LUFS）与 `sfx` 两组，**每个 SFX 同步点周围把音乐压低 3 dB**（duck）。
  3. `form` 里 **bar 0 精确锚定在 drop**，intro/build/drop/outro 四段；`chord_at(t)` 给出任意时刻的和弦 → 调性 SFX 不会跑调。

**结论：不要移植，要接入。** 把 `mgaudio` 作为 Python 子进程工具（本仓已有 `vo.py` 先例，且 uv 是既定约定），我们保留 `audio-mix.mjs` 的混音/ducking，只把"选 loop + 手工 TRIM"换成"给 recipe + bpm + drop 时间，出 wav"。收益是配乐**可版本化、可复现、换机不失效**。

**必须先验证的一点（对抗审查）**：`mgaudio` 是为 **10 秒** MG demo 设计的，`duration=10` 是默认值，form 的段落长度也是按 10s 排的。本仓成片 60–100s。落地前必须实测 `duration=90` 时的段落扩展是否合理，否则会把"配乐失效"换成"配乐单调"。这是**唯一可能否决这项的理由**，不实测不落地。

## 四、C 级：只抄概念，不抄代码

### C1. 配方卡 schema（shotcraft，19.2k★ 但宿主不兼容）

shotcraft 是 Remotion/React，与本仓 Skia 直出无法复用代码。但它的**知识封装格式**是本批里最成熟的：

```
frontmatter: name / 一句话 / 适用 / 时长 / 能量 / 标签
正文: 意图 → 选型（表格：式/做法/适用）→ 参数表（典型值 + 调节手感）→ 已知坑 → 参考实现
```

对比本仓 `kits/*/README.md`：**缺「参数表」与「已知坑」两列**。我们的坑记在 `MEMORY.md`（按主题），不记在段型旁边。结果就是写新片时要同时翻两处。

参数表的写法尤其值得抄：不是"参数说明"，而是**「调节手感」**——「0.95 起步才有闪光灯的爆点；衰减 >6f 变柔光转场，失去快门感」。这是"改这个数会发生什么"的因果，不是取值范围。

### C2. 三方案预览（xilo，401★，只有 SKILL.md）

流程是：给 3 个差异极大的方案 → 各渲一张关键帧或 2–4s 小样 → 用户确认 → 写 `brief.md` → 才开始做。

价值在成本结构：**「渲完才发现方向错了」是最贵的一步，预览把它挪到开始之前**。

本仓具备落地的全部条件（`caps` + `validate` + 一张关键帧的成本只有几十毫秒），但这是**产品决策**，不是技术债。要做的话是 `api` 加一个 `preview` 动作，返回 3 套 style 各一张图。不建议现在做。

### C3. 解说语法的正交维度（huashu）

huashu 的 8 种语法（3b1b / Keynote / 财经图表 / Kurzgesagt / Vox / 白板 / storytime / 动态文字）与本仓的 11 种段型（hero/point/number/compare/steps/quote/checklist/outro/broll/grid/chart）**是两个正交维度**：

- 段型决定**讲什么**（一段话是"对比"还是"步骤"）
- 语法决定**怎么演**（同一个"对比"，可以是 Vox 的调查桌，也可以是 3b1b 的形变）

本仓只有前者。补后者等于给每个段型再乘一个视觉维度，工程量按段型数 × 语法数增长。**明确不建议现在做**，但值得记进架构备忘：如果将来出现"同一个段型在不同片子里样子太像"的反馈，这就是解法。

另一个可单独吸收的判断（huashu 片段契约）：**单个片段超过 8 秒会读成一页 PPT**（「一个版式到底、要点越堆越长、背景从头死到尾」），`render.py` 会在超过时于开头和结尾各打一次警告但不报错。

这条与本仓 `clampTimes` 压到 ≤3.0s 是同一类直觉的不同刻度。我们更严，说明方向是对的，不必改。

## 七、一条方法论层面的收获

这批 Skill 的价值不在"能画什么"，而在**它们把「逐帧渲染管线」的专属缺陷写成了检查项**：

- 状态泄漏（`--check-determinism`）
- 关键帧卡点（前 0.1s / 后 0.35s 拼图）
- 关键词锚点（不写死秒数）
- 片段过长（>8s 警告）
- 丰富度（相邻格差 + "去掉开场第 1 对"）

这些缺陷的共同点是：**按顺序渲染时看不出来，单帧或乱序时才暴露**。本仓同样受这类缺陷支配（`renderFrame(t)` 纯函数、`ctx` 复用、`scenes` 数组按序），所以这批检查项的迁移价值高于任何一段视觉代码。

### 与原提案的三处偏离（均为实测后的修正）

1. **A1 拆成双锚点**。原设想只用一个 `$mark`。实测发现本仓两套时间语义并存：`args.cards[][1]` 是绝对秒，`screens[].at` 是段内相对秒，同一数值在两边含义不同，无法自动推断。改为 `$mark`（绝对）/ `$markRel`（段内相对）显式区分，写错时报错并提示该用哪个。
2. **A1 的数组分支是必需项**。`cards: [["标题", {$mark}]]` 这种元组是 paper 的主力写法；第一版只在对象分支判锚点形状，漏掉 4/5 个用例，静默留下未解析对象。

## 九、对抗审查（2026-11-14 18:40）

对 A/B/C 全部落地项做了一次反向检查，**结论是：交付了能力，但没有兑现价值**。

### 9.1 零使用：三项新能力没有任何一支成片用过

| 能力 | 声称解决 | 实际使用 |
|---|---|---|
| `wordTimes` 关键词锚点 | 消除"手写秒数"整类事故 | `grep -rl wordTimes content/ kits/` → **零份** |
| `args.camera` 段级运镜 | 长片 PPT 感 | `grep -rl '"camera"' content/*/params-abs.json` → **零支** |
| `--synth` 代码合成配乐 | 换机失效 | 只在 benford 上跑过一次，未进 `make.sh` |

原因不在实现，在**链路断开**：

- 锚点缺「生产器」。dashi 有 `生成timeline.mjs` 从字级时间算 marks，我们只有 `src/temporal.mjs` 里的解析器。
  要用锚点得手工写 `wordTimes` 表——那比手写秒数更麻烦。**这是 A1 的真实完成度：50%。**
- 运镜与配乐缺「默认值」。`camera` 默认关闭是对的（零回归），但没有"哪种段型适合配什么镜头"的预设，
  写新片的人不会主动加。

### 9.2 验证缺失：两个改动从未实跑

- `publish-pack` 的 `tail()` 只做了 `node --check`，**实际跑起来直接崩**（TDZ）。已修。
  教训：语法检查不是验证，`node --check` 通过 ≠ 能运行。
- `--check-determinism` 首轮只在 3 个 preset 上跑过。本次补测 6 支真实片
  （benford / birthday-paradox / selection-bias / round-window / reno-order / gut-antibiotic），
  全部"一致"——结论不变，但此前的证据面只有 3/22。

### 9.3 参数表的"手感"多数是推断

11 张卡里，带**实测现场**的结论只有 8 条（已单列在 `segments/README.md` 的可信度表）。
其余「读作一闪」「观众会开始等」是从版面几何和时长外推的，没有看过片。

这不是不可接受，但**不能当成经验卖**。已在卡片目录首页加分级标注：实测 / 算术 / 推断。

### 9.4 优先级次序错了

按"用户实际遇到的痛"排序应是 **A3（拼图）> B1（运镜）≈ B2（配乐）> A2（确定性）> A1（锚点）> C1（文档）**；
实际执行顺序是 A2 → A1 → A3 → A4 → B1 → B2 → C1。

也就是说：**把工程上最优雅的排在了最前面**。确定性检查三支 kit 全干净、真实片 6 支全干净——
说明这个风险目前没有实际发生过；而拼图工具第一次跑就抓到一个真实问题（字幕比口播晚）。

### 9.5 一条错误记忆被信了多轮

`MEMORY.md` 里"注入上限约 12KB，超了会被截断"这条，我一直当硬约束，直到实测文件 16.5KB
而注入内容完整到 §十二才发现过时。**记忆条目本身也需要定期对抗审查**，尤其是带具体数字的。

### 9.6 建议的补救（按价值排序）

1. **给锚点补生产器**：从 `script.json` 的字级时间（或"按字数摊"的近似，误差 ±0.45s 已够）生成
   `wordTimes`，让内容侧只写词不写秒。没有这一步，A1 等于没做。
2. **至少一支片真用运镜**：挑 benford 的 hero/quote/outro（静态构图段），加 `push z=1.06 dur=1.2`，
   出片后逐帧看推的节奏。不做这一步，B1 只是"能跑"。
3. **把 `--synth` 写进 `make.sh`**：让新片默认走代码合成，Apple Loops 退为可选。
4. 段型卡每用一次回来改一次（把"推断"升级成"实测"）。
