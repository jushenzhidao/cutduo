01先解决「看不见」

默认 access_log 只有状态码和字节数，回答不了「慢在哪一层」。这是本次监测的第一件事。

原 vhost 用的是 nginx 默认 combined 格式，既没有 $request_time， 也没有 $upstream_response_time。后果是请求慢的时候只知道「慢」， 不知道慢在 TLS、网络、nginx 还是应用。而这两者的差额最容易被误判 —— 端到端里包含客户端上行时间，把它当服务端耗时会得出完全错误的优化方向（§03 的上传数据即是例证）。

处理方式是只增不改：在原 access_log 之外加第二条日志与独立 log_format， 原日志格式、宝塔统计、其他 20 多个 vhost 全部不动。

# /www/server/panel/vhost/nginx/mcp.cutduo.com.conf
log_format cutduo_perf escape=json '{"ts":"$time_iso8601","ip":"$remote_addr",
  "m":"$request_method","uri":"$request_uri","st":$status,"rt":$request_time,
  "urt":"$upstream_response_time","uht":"$upstream_header_time",
  "uct":"$upstream_connect_time","body":$body_bytes_sent,
  "req":$request_length,"ua":"$http_user_agent"}';
access_log /www/wwwlogs/mcp.cutduo.com.perf.log cutduo_perf;   # 新增一行
  • 改前备份 mcp.cutduo.com.conf.bak-perf-20261110-011410，nginx -t 通过后才 reload；
  • uht（上游首字节）是中途补的：大文件下载时 urt 会跟随客户端消费速度， 没有 TTFB 就分不清是服务端慢还是客户端慢 —— 见 §03；
  • 新增 /etc/logrotate.d/mcp-cutduo-perf（daily / 50 M / 保留 7 份 / kill -USR1）。 宝塔的切割只处理 <domain>.log，不管这条新日志，不加就会被写满；
  • 解析脚本入库：renderd/tests/perf_report.py，按端点出 p50/p95/p99，并把上传拆成「客户端」与「服务端」两列。

五个结论

  • 同一台机器、同样 450 帧，实测跨度为 24.5–54.9 s。这段跨度里有两种成本， 本轮只证明了它们存在，没有分离它们。
  • 宿主负载的振幅本身是个风险：15 分钟采样窗口内 load 从 15.1 冲到 74.0（64 核，已超卖）， 同机还跑着 20+ 个业务（同期两个 clickhouse 各占约 80% CPU）。 渲染既被 4 核配额限制，又与邻居争内存带宽 —— p95 延迟不由我们自己决定。
  • 校验是第二大固定成本：450 帧 7.07–16.06 s，与帧数严格线性 —— 这个形状说明它在做逐帧全解码（§05-B2）， 与负载无关的部分是确定的。
  • mezz 缓存有效，但只对「同素材」有效：任务 3 的 0.41 s 是命中缓存； 任务 4/5 的 15.4 s 是 3 个全新素材首次归一化，每个约 5.1 s。
  • 渲染被 4 核配额卡住：worker 峰值 CPU 400–412%（配额 400%）—— 配额打满不等于拿到 4 核的真实算力，超卖时同份额的 CPU 时间产出更少。

资源侧另记一笔：api 容器在预检期间峰值 178%（配额 200%）、内存 52→165 MiB； PG 常驻约 65 MiB；可用内存始终 > 24 GB。

05五个瓶颈，按「证据 → 代价 → 修法」排列

每条都给了可复现的判据，不是凭感觉的优化清单。

B1 · 每个 HTTP 请求都新建一条 PG 连接 P0

证据：连打 20 次 GET /v1/jobs，PG 的 sessions 从 3666 → 3687， 即 21 条；同样 20 次 /healthz（不碰 DB）只涨 1 条。 拆开测：psycopg.connect 11–27 ms，同连接上查询 0.81–0.91 ms，get_tenant 热态 0.30 ms。 那 25–47 ms 里绝大部分是建连，不是查询。

代价：单请求固定多付 20–30 ms；并发时更糟 —— 10 个并发请求最慢 5 个为 124–139 ms，是单请求的 4–5 倍，因为 SCRAM 认证在 PG 侧串行完成。 MCP 客户端一次任务往往并行发多个工具调用，放大正好落在最敏感处。

根因：ThreadingHTTPServer 每请求开一个短命线程， 连接存在 threading.local 里 —— 线程一换，连接就没了。 上一轮为修 SQLite 的 fd 泄漏在请求结束时显式 close_thread_connection()， 对 SQLite 正确，对 PG 等于每请求付一次握手。

修法：给 PostgresStore 加连接池（psycopg_pool.ConnectionPool 或自建 idle 列表 + checkout/checkin）， 请求结束归还而不是关闭。预期 DB 端点 30 ms → 3 ms，10 并发 139 ms → <15 ms。 不动 SQL、不动契约、不动鉴权。

B2 · 校验阶段把同一个文件全解码 3 遍 P0

证据：validate.py 里 black_ranges() 一遍 blackdetect、 evidence() 里 contact sheet 一遍（select + tile）、last frame 一遍（要解到第 N 帧 = 全解码）， 再加音频 ebur128 与 showwavespic 两遍 —— 合计 3 次视频全解码 + 2 次音频全解码。实测耗时与帧数严格线性，且随码率放大。

代价：450 帧 7.07–16.06 s，占单任务 28–29%；180 帧 3.86 s，占 32%。片子越短，相对成本越高。

修法：把 blackdetect 与抽帧合并进一个 filtergraph （[0:v]split → 一路 blackdetect、一路 select+tile，-map 多输出），音频同理。 预期 7.1 s → 约 2.5 s（10 Mbps 素材 16 s → 约 5.5 s）。 合并后必须逐一比对断言输入（黑场区间、contact sheet 帧号），否则等于改了验收口径。

B3 · 为补两个元数据字段，把整段视频重编一遍 P0

现象：任务 4/5 的归一化各花 15.2–15.5 s（3 个素材，每个约 5.1 s）， 而这两批素材只缺两样东西：色彩标记（COLOR_UNTAGGED）和音轨（NO_AUDIO）。 代码里 passthrough = (not actions) and not audio_role —— 只要有一条 action，就走 libx264 整片重编。

实测对照（同一素材 b60b6e58…，1080×1920 / 150 帧 / 6.2 MB，缺色彩标记且无音轨）：

适用边界（必须写进代码，不能凭动作名判断）： 仅当 action 集合 ⊆ {TAG_COLOR, AUDIO_SYNTH}， 且素材的宽高 / 帧率 / 像素格式 / SAR / 旋转已经等于目标规格时才允许 copy。 任何几何、帧率、像素格式或 HDR 相关的动作仍然必须重编 —— 那些不是元数据，改不了码流之外的东西。

B4 · 单 worker 串行，且成本随源码率翻倍 P1

1 个 worker、WORKER_CONCURRENCY=1，任务严格串行。 按实测 p50 32.4 s 算，吞吐上限约 1.9 任务/分钟；若素材都是 10 Mbps 档，则只有 1.1 任务/分钟。

宿主 64 核、同期 load 9.7–32.9、可用内存 > 24 GB，再加 2–3 个 worker 容器有余量。 建议按「每副本 4 核」扩容，而不是调大 concurrency —— 同容器内并发会和渲染抢 CPU， 日志与崩溃恢复也会混在一起（上一轮已定过这个取舍）。

B5 · 素材预检在请求线程里跑，且吃满 API 的 2 核 P2

证据：validate_render 实测 2.62 s（2 个素材）、6.39 s、10.61 s、11.82 s（3 个素材，10 Mbps）； 同期 api 容器 CPU 峰值 178%、内存 52→165 MiB。

代价：预检是 CPU 密集（抽样解码 + 字体栅格化），跑在 API 进程里。 两个客户同时提交就会把 API 的 2 核吃满，连带拖慢「查任务状态」这类轻请求 —— 而轮询恰恰是 Agent 最频繁的动作。这条在 blockers.md 里原是 P2，本轮给了它具体数字。

修法：预检改为入队前的独立阶段，或至少加 2 并发信号量兜底。

06两个只在真实调用里才会发现的现象

① 每租户 10 QPS 是共享预算，自测探针都能撞上

连续快速打 12 次 MCP 工具调用，第 12 次返回 E_RATE_LIMITED「超过 10 req/s」， 并且随后 3 次 GET /v1/jobs/{id} 也被限流 —— 说明限流按租户共享、跨端点生效。 单个 Agent 顺序调用没问题；若客户端把 tools/call 并发发（例如同时查 6 个任务状态）， 很容易在 1 秒窗口内撞顶。错误是 retryable=true， 客户端必须实现退避重试，否则会表现为「偶发失败」。

建议：客户端侧限并发（≤5），或把 RENDERD_QUOTA_QPS 从 10 调到 20–30。 这是产品口径，不是 bug，所以没动。

② 公网入口有持续扫描，占日志与一点 CPU

00:57–01:12 的 116 条请求里 55 条 404 来自公网扫描器： /graphql、/api/gql、/server-status、 /v2/_catalog、/.env、/.git/config， 以及一条 Atlassian Jira 的路径穿越尝试。全部被 404 挡下，未触发限速，也未进入应用。

属于「有公网 IP + 有 DNS 记录」的常态。可选处置：对已知扫描路径 return 444 （不写日志、不回包），把噪音降到接近零。不改也不影响安全模型 —— 鉴权在应用层。

09补测：三处「输出字节不变」的优化

上面五条都需要改行为或重启服务。这一节是另外三条 —— 改完输出文件逐字节相同，属于可以放心上的优化。

出发点是一个数字对不上：纯解码+编码 150 帧只要 1.9 s（≈80 fps）， 而线上渲染 450 帧要 17–23 s（≈20–27 fps）。差的不是编码器，是滤镜链。 逐项拆开验证（同一 mezz、同一编码参数、crf20/veryfast/4 线程）：

纯解码 + 编码1 855–1 932 ms——
+ 空转 scale/pad/setsar（尺寸已达标）1 953 ms+4%是
+ 整帧 1080×1920 RGBA 叠加（现状）5 661 ms+195%基准

为什么文字层这么贵：栅格化用的是 Image.new("RGBA", (W, H)) —— 整帧 1080×1920， 而实测文字只占 0.8%–3.7% 的面积（bbox 例如 591×92 / 1080×1920）。 剩下 96% 以上的像素是透明的，但每帧仍要参与一次全帧 alpha 混合。 裁剪后叠加成本从 3.8 s 降到 0.45 s，9 倍，且像素完全相同 —— 因为透明区域本来就不影响结果。

需要接受的代价

  • 图层 PNG 变了 → 缓存键变 → 全部渲染缓存失效一次。因为输出逐字节相同， 重算不会产生与旧产物不一致的成片，所以这次失效是安全的（不是 §09 之外那种「拿旧片」的风险）。
  • COMPILE_REV 要 bump；evidence_sha256 里 contact sheet / last frame 的哈希会变一次 （命令变了，文件字节其实相同 → 这两项其实不变，只有 argv 版本变了）。
  • 裁剪依赖 Layer.bbox，而它已经是安全区校验的输入 —— 不需要新增几何计算， 但要把「bbox 为空」（纯空白文字）这一分支显式处理成「不叠加」。

三个结论

  • 没有被打挂。全程 0 个 5xx、0 个失败任务、PG 连接恒为 9、健康检查稳定 1.5 ms。 拒绝全部以 429 返回 —— 这是正确的降级形态。
  • 瓶颈是限流，不是算力。api 峰值 153%/200%，从未打满；真正的墙是每租户 10 QPS。 想让 Agent 并行，先解决那条与成本无关的计数（见 §06-①）。
  • MCP 层相对渲染能力是 6–33 倍过剩。8 rps 干净 ≈ 480 请求/分钟； 一次渲染流程约 13 个请求（3 上传 + validate + submit + 8 次轮询 + 下载）， 折合 约 37 个流程/分钟的请求预算；而单 worker 只能做 5.6 个（180 帧）或 1.1–2.4 个（450 帧）。 结论：再优化 MCP 吞吐没有意义，扩 worker 副本或压渲染成本才是。
