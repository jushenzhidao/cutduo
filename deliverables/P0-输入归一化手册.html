01为什么这个阶段不能跳

先讲一件会决定后面所有工期可信度的事。

原方案把「跑通产品」定义为"云端 melt 命令行 + XML 模板渲染，打通任务队列 → 成片链路"。这个定义里没有输入归一化。后果是：输入侧的任何问题，最终都会以"渲染 bug"的形态出现在你面前——HDR 素材渲出来发灰，你会去查色彩管理；VFR 素材音画不同步，你会去查时间线；旋转素材出横版，你会去查 scale 参数。每一次都会花掉半天到两天，而且修完一个还会再来一个。

这 21 条语料里，只有 1 条能零转码直通。3 条必须在入队前就拒绝——它们不是"渲染失败"，是"根本不该开始"。剩下 17 条能救，但其中 15 条救完会改变素材语义，必须让客户知道。

这一阶段的验收标准 不是"能渲染了"，而是：21/21 条语料都被正确分类——该直通的直通、该归一化的归一化后校验通过、该拒绝的报对错误码。达不到这个，先别装 melt。

02三段式：观测 / 决策 / 执行

刻意拆成三个函数，而不是写成一个"检测到就处理"的大函数。

probe()

只观测

原始 ffprobe + 规范化描述 + 风险标记。不改动任何字节。输出可入库、可比对。

→
decide()

只决策

标记 → 声明式动作序列 + 错误码 + 警告。不碰文件。这份 JSON 可以 review、可以回放、可以入库对账。

→
normalize()

只执行

按动作序列拼 filtergraph，输出 canonical 中间片，再跑一次 probe 做自校验。

拆开的收益很具体：客户问"这条素材为什么被转成了这样"，你能直接把 plans/<id>.json 甩出去——里面写着每一个动作的触发原因（"TONEMAP_HDR ← transfer=arib-std-b67 / primaries=bt2020"）。如果三者写在一起，这个问题永远答不上来，只能重新猜一遍。

canonical 中间片规格（不可协商）

维度规格为什么
时间整数帧，CFR 30fps浮点秒在 29.97 下必然漂移；漂 1 帧的伤害比换编码器大得多（见主报告 M2/M3）

几何保留源宽高比，只限长边归一化阶段不做 cover/contain —— 那是模板的事，此处裁掉就不可逆

04三条必须拒绝的

这三个的共同点：任何"容错"处理都是在替客户做一个他不知道自己做了的决定。

错误码检出点为什么不能猜
E_INPUT_UNREADABLE
c08_zero_bytes		 入库，stat + ffprobe 0 字节文件的容错空间是零。补一个黑帧？那是对一支客户以为有内容的片子撒谎。
E_INPUT_AUDIO_ONLY
c19_audio_only		 入库，流类型检查 纯音频被投到视频素材位，说明上游参数组装错了。此处静默补黑帧，会把一个上游 bug 变成一个下游谜题。
E_INPUT_TRUNCATED
c09_truncated		 入库，抽样解码 moov 在头、mdat 被截断：容器说 20 秒，实际只能解 12 秒。它会被 ffprobe 判为"可读"，只有真解码才暴露。这是最危险的一类——所有基于元数据的检查都会放行。
关于 c09 这条值得单独说：ffprobe 说它时长 20 秒、分辨率正常、编码正常。元数据层面它完全健康。只有把帧真解一遍才会在 12 秒处炸。所以入库必须有一次抽样解码——而且生产环境应该对整片跑一次，抽样只是为了不让入库耗时失控。

05五类"能救但改变了语义"的

技术上成功，商业上必须告知。这类是客服工单的主要来源。

情况我们的处理必须告知客户什么
HDR（HLG / PQ）TONEMAP_HDR：colorspace 直转 BT.709直转不是 tone curve。高光会压平、饱和度会偏。正式产品应换 libplacebo / zimg，在此之前这类素材应标"预览级"。
无音轨AUDIO_SYNTH：补 48k 立体声静音时长会以视频为准。如果模板依赖音频节拍（卡点），成片会完全错位，必须人工确认。
多音轨AUDIO_PICK_FIRST：取第一条丢弃的可能是原声也可能是配音。这条如果不告知，交付事故率接近 100%。
内嵌字幕DROP_SUBS：不烧录、不转资产客户会说"字幕没了"。正确做法是把它转成字幕资产进 IR，这是 P1 的范围，P0 必须显式记录成警告。
VFR / 高帧率CFR / DECIMATE帧数会变。120fps 降到 30fps 是丢 3/4 的帧，慢动作素材会失去慢动作感。

06三个只有真跑才会发现的坑

这三条不是从文档里抄的，是这一轮跑语料撞出来的。每一条都会让"看起来正确"的产物在客户手里出错。

libx264 不写 VUI 色彩标记-color_primaries 单独给没用

只传 -color_primaries bt709 -color_trc bt709，ffprobe 会读到 primaries=unknown / transfer=unknown，只有 color_space 落了。成片在播放器里各显各的。这条坑让本手册的干净对照组第一次跑就失败了——它本来就是我用来当"免检"基准的。

# ✗ 不够
-color_primaries bt709 -color_trc bt709 -colorspace bt709
# ✓ 必须显式进 SPS VUI
-x264-params colorprim=bt709:transfer=bt709:colormatrix=bt709:range=tv
奇数分辨率：scale 是拉伸，crop 才是裁切641×481 → 640×480 还是 640×482

奇数边必须偶数化（yuv420p 要求），但两种做法结果完全不同：scale=trunc(iw/2)*2 会把 641 压成 640——整幅画横向缩了 1/641，是变形；用 crop 则丢掉最后一列像素，没有变形。默认应该裁。

# ✗ 变形
scale=trunc(iw/2)*2:trunc(ih/2)*2
# ✓ 丢 1px，不变形
crop=trunc(iw/2)*2:trunc(ih/2)*2
ffmpeg 9 已不能靠 metadata 写旋转矩阵-metadata:s:v rotate=90 静默失效

老办法 -metadata:s:v:0 rotate=90 在新版上不报错，但也不写显示矩阵——你会得到一条"看起来有 rotation 元数据、实际 ffprobe 读不到"的片子，测试用例因此假通过。必须两步：先出片，再用 -display_rotation 重封装。

ffmpeg -y -i in.mp4 -c:v libx264 base.mp4
ffmpeg -y -display_rotation 90 -i base.mp4 -c copy out.mov

07失败分类学（P0 定稿版）

code 是契约，message 是叙事。二者不可互换——Agent 靠 code 决策，人靠 message 理解。

code阶段可重试客户可见文案

08进 P1 之前的检查清单

八条，全部可验证。少一条，P1 的第一个 bug 就会伪装成渲染问题。

  • 21/21 语料分类正确。直通、归一化、拒绝三类都归对，且归一化后产物通过 8 项规格校验。
  • 失误率有基线。记录当前每条语料的入库耗时，P1 的端到端预算从这里往下算。
  • 零转码路径存在。1/21 条直通——这条路径决定了客户量级上来后的成本曲线。
  • 色彩四标齐全（primaries / transfer / matrix / range），且已用 -x264-params 落进 SPS VUI 验证过。
  • 抽样解码在入库链路里，且对 c09 这类"元数据健康"的截断文件能报警。
  • 决策 JSON 入库，能回答"这条素材为什么被转成这样"。
  • 警告能透传到客户——不是打在日志里，是进 receipt。
  • 拒绝入队不产生渲染成本，且返回的 code 与文案能让人立刻知道该改什么。

怎么重跑：cd cutproof && python3 corpus/gen_dirty.py && python3 ingest.py all。语料全部是 lavfi 合成的，无版权风险、体积可控（约 97 MB）、可确定性复现。表格数据来自 res/matrix.json，本页由 make_p0_report.py 生成，没有任何一个数字是手填的。

已知边界：语料是合成的，能复现"故障模式"但不能复现"真实拍摄素材的噪声分布"；上线前仍需灌入 50–100 条真实客户素材做一次回归。HDR 转换用的是 colorspace 直转而非 tone curve（本机 ffmpeg 无 zimg），正式产品应替换为 libplacebo。抽样解码默认 15 秒，长素材的尾部损坏不会被抓到。
