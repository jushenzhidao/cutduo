## 一、T1：原计划被证伪，改成更有用的东西

### 1.1 为什么放弃「锚点生产器」

原计划：从 `script.json` 的字级时间生成 `wordTimes`，让内容侧只写词不写秒。

实测发现**前提不成立**：

| 来源 | 文案 | 关系 |
|---|---|---|
| 口播原文（captions） | "翻开一本人文地理年鉴，把里面所有数字的第一个数字取出来。" | — |
| 画面文案（screens） | "第一个数字是 1 的" | **改写，不是子串** |

本仓的画面文案是**压缩改写**的，不是口播原句。所以"按口播查词定位画面元素"根本查不到。dashi 能做锚点，是因为它的分镜文案直接取自口播。

**结论：`wordTimes` 能力保留（无害，已有 9 个单测），但不是主线。** 主线换成下面这个。

### 1.2 真正的缺口：越界静默

`paper` 的 `scenes[].args` 时刻是**绝对秒**。越界不会报错——`pr(t, at, at+0.52)` 在该段内永远返回 0，元素**永不出现**，成片只是少一块。

MEMORY §五 记了这一整类事故，但从来没有自动检查。

### 1.3 交付

| 项 | 结果 |
|---|---|
| `tools/check-times.mjs` | 静态扫描，438 个时刻 / 36 份 params，秒级 |
| `src/temporal.mjs` 的 `auditTiming` | 接入，**默认拦**（退出码 2） |

### 1.4 抓到的真实错误

`content/sample-1000` 与 `content/sample-mean` 的 compare 段：

```json
{ "leftAt": 0.5, "rightAt": 1.6, "strikeAt": 9 }   ← 段只有 4.41s
```

`strikeAt: 9` 是段内秒，但段只有 4.41s ⇒ 划线永不出现。build 忠实地换算成 `t0+9=50.04`，越界 4.6s。

**修复**：`strikeAt: 9` → `2.1`（`rightAt + 0.5`）。修复后划线出现（`deliverables/uv-run/T1-timecheck/strike-visible-after-fix.png`）。

### 1.5 关键发现：paper 与 science 的时间语义相反

接入时第一版把 science 全拦死了，报 `diagram.callouts[0].at=1.40 早于段起点 19.50s`。

根因：**science 的 `renderFrame` 传 `localT`（段内已过秒数），args 时刻是段内相对秒**；paper 传绝对 `t`。检查器必须按 `params.segments` 是否存在切换两种判据。

这条 MEMORY 里没记，已补。

## 二、T2：运镜在真实内容上遇到结构冲突

### 2.1 冲突

本仓分镜几乎全是**一拍拆多段**（同一份 screens 重放 2–5 遍）。按段加相机 → 观众看到「推近 → 跳回 1.0 → 再推近」。

### 2.2 补的能力：`hold`

`src/camera.mjs` 新增 `{kind:'hold', z}`：整段固定在某个倍数。配合 push/pull 可以做到跨段连续：

```
hero[0] push → hero[1] hold → hero[2] pull
```

单测：四个衔接点全等 1.0800。

### 2.3 补的工具：`tools/apply-camera.mjs`

按「连续同型段组」（≈一拍）自动编排：1 段 push / 2 段 push+pull / ≥3 段 push+hold…+pull。
默认拒绝 `chart`/`grid`/`steps`/`number` 这类"元素自己在动"的段型（`--force` 可强制）。

### 2.4 两组成片

| 片 | 配置 | 结果 |
|---|---|---|
| `round-window` | hero×3 + quote×4，z=1.06 | 5459 帧 / 90.98s / gate PASS / 确定性 PASS |
| `info-check` | quote（单段不重放），z=1.08 | 3314 帧 / 55.23s / gate PASS |

**连续性验证**（info-check 的 quote）：

| 时刻 | 段内经过 | z | 与原版 PSNR |
|---|---|---|---|
| 26.0s | 0.18s | 1.0006 | **inf**（完全一致） |
| 29.0s | 3.18s | 1.036 | 19.44 dB |
| 32.4s | 6.58s | 1.078 | 18.69 dB |

段首 `inf` 是最有说服力的一条：**从 1.0 起推，段首与不加相机逐像素相同**，不会突然放大。

衔接点验证：相机版 18.47 dB vs 无相机版 18.94 dB，差异几乎相同 ⇒ 衔接处没有相机跳变（差异来自内容重放）。

## 四、T4：用卡片规则核查真实片，抓出 7 处违规

`segments/number.md` 写着「**`from` 不要写 0**——中间值会当事实上屏」。核查真实片：

| 片 | 违规段 | 参数 |
|---|---|---|
| `round-window` | 3 段 | `from=0 value=500毫巴` |
| `benford` | 2 段 | `from=0 value=30.1%` |
| `info-check` | 2 段 | `from=0 value=3个问题` |

**全部 7 个 number 段都是 `from=0`。**

扫片已经拍下后果：round-window 显示过 `0 毫巴`、`154 毫巴`、`412 毫巴`、`498 毫巴`——标签是"机身内外压差"，这些中间值等于画了不存在的事实。

**修复范围**：只改 `round-window`（作为验证案例），`from=0` → `from=500`。

修复后扫片：number 段稳定显示 `500 毫巴`，中间值全部消失。

**未改 `benford` / `info-check`**：它们是要交付的片，改数字滚动会改变观感（数字不再滚动，只有圆环在走）。这属于内容决策，留给你定。改法一行：`script.json` 的 number screen 里 `"from"` 改成与 `"value"` 相同。

## 五、对抗审查：本轮发现的问题

### 5.1 我自己引入的崩溃（已修）

`tools/publish-pack.mjs` 的 `tail()` 写成 `const` 箭头函数在第 93 行，`pickCoverTime()` 在第 60 行调用 ⇒ TDZ `Cannot access 'tail' before initialization`。上一轮我只跑了 `node --check` 就报"已落地"。

已改成函数声明，实跑通过（benford 封面 31.46s）。

### 5.2 我算错的越界（第一次扫描）

第一版扫描脚本拿"段长"判定绝对秒，得出"190 处越界"的错误结论。**如果照着修，会破坏所有正常片。**

确认语义（`pr(t,...)` 用绝对 t，画面在 6.5s 时第二行 7.98s 还没到，完全正确）后重扫，真越界只有 4 处。

### 5.3 扫片暴露的既有内容问题（非本次引入，未修）

`round-window` 的扫片显示：

- 同一标题「没有一扇是方的」在 0–14s 内出现 **3 次**（一拍拆 3 段重放）
- compare 段「省空间 vs 力分散」/「方形窗 vs 全圆窗」交替重复
- quote 段「圆角不是审美」→「先别急着说审美」→「这不是妥协」→ 又回「圆角不是审美」
- 第 3 格几乎空白（只有眉标和卡片）

这些都是「一拍拆多段重放」的既有后果，与运镜无关。**建议单独立项处理**（要么让拆段用不同的 screens，要么让同拍的第二段不重放揭示动画）。

### 5.4 未验证的项

- `round-window` 的运镜版**没有逐帧看完 91 秒**，只看了扫片和 3 张抽帧。推的节奏是否"顺"，需要你正常速度看一遍。
