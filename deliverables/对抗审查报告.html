01威胁模型

先假设攻击者是谁，否则测试会变成"检查功能列表"。

假设攻击者持有合法 token——这是最现实的场景：SaaS 的付费客户，或者被泄露的密钥。完全未认证的攻击者只能触达 /healthz 与 /metrics。

资产攻击者想做什么缓解
容器内文件通过素材路径读任意文件路径围栏（resolve + 白名单）
内网服务通过 callback_url 做 SSRF 探测协议 + 目标 IP 白名单
其他租户的数据越权读任务 / 回执 / 成片租户隔离 + 签名绑定 job_id
算力与内存一条请求打满集群九道容量护栏
数据库SQL 注入全参数化，无字符串拼接
不在威胁模型内 拿到宿主 root、拿到 RENDERD_SECRET、物理接触磁盘。这些情况下应用层防护无效，属于基础设施安全。

02两个 critical

都不是"配置问题"，是设计漏洞。修复前后的行为差异都有实测证据。

任意文件读取B01 · file:///etc/passwd

提交渲染时把素材地址写成 file:///etc/passwd，服务会真的去打开它。证据是返回码：

修复前： 422 E_INPUT_AUDIO_ONLY   ← 说明 ffprobe 已经解析过这个文件
修复后： 403 E_MEDIA_FORBIDDEN   ← 在解析之前就被挡住

多租户环境下这意味着：租户 A 可以枚举容器内任意路径是否存在，读到别的租户的成片（路径可猜），或者读配置文件。

修法：resolve_uri() 统一围栏到 media/，Path.resolve() 顺带解开符号链接；upload: 名走 ^[A-Za-z0-9][A-Za-z0-9._-]{0,127}$；越界一律 403。

全 worker 失联时任务永久卡死租约回收的单点故障

租约回收原先只写在 Worker.run_forever() 里。用 docker compose kill -9 worker 之后：

t+0s   任务 running
t+18s  任务 仍然 running     ← 没有任何进程在扫过期租约
t+30s  拉起 worker → 立刻被回收 → attempts=2 → 重新渲染成功

也就是说：worker 全挂的那段时间，客户的任务是死状态，而且 API 还在正常接受新任务，队列越积越多。

修法：抽出独立 start_reaper()，API 进程默认启动，另提供 renderd reaper 供分离部署。复测：kill 后 15s 内识别、自动重排、worker 拉起后自愈。

05容器与稳定性

对抗测试之外，还跑了四条真实链路。

  • 容器内端到端 10/10 —— 上传 → 预检 → 三模板提交 → 轮询 → 回执 → 下载 → 幂等重放。成片抽帧确认中文正常（Noto CJK 回退），无豆腐块。
  • Compose 11/11 —— api/worker 分离、kill -9 崩溃、租约回收、任务自愈（attempts=2）、重启 api 后任务与缓存都在。
  • 多 worker 并发 7/7 —— 3 个 worker、6 线程并发提交 12 条：12 个不同 job、每条恰好 1 次 rendering、attempts 全为 1、无租约回收；并发重放 12/12 命中同一 job。
  • 长稳 30 条 —— 全部成功。首批 p50 5132ms，第二批（命中缓存）p50 807ms；内存 156.9 → 168.6 → 170.3 MiB，第二批仅 +1.7 MiB，判断为首批的堆预热而非泄漏；磁盘按每条约 5.5MB 线性增长。
容器带来的两个真实功能缺陷 .ttc 只注册 face 0（Noto CJK 的 face 0 是 JP，导致 SC 永远查不到，一路回退到无 CJK 的 DejaVu）； 同族多字重按字典序排在 Bold（正文整篇变粗）。两者在宿主机上都不会暴露——这就是必须进容器测的理由。

06残余风险

没修的、修不动的、和需要基础设施配合的。

风险影响建议
DNS rebinding 绕过 SSRF 校验提交时解析到公网、投递时解析到内网投递时重新解析 + 网络层 egress 白名单
签名 URL 不绑定租户链接泄露即可下载（同 S3 presigned 语义）需要时把 tenant 签进 sig
/metrics 公开暴露任务总量与状态分布反代加 IP 白名单
/v1/assets 无存储配额可刷满磁盘（只有渲染时长配额）加租户级存储配额
SQLite 单机不能多机横向扩换 Postgres / Redis 队列
无 TLS / 无 WAF明文传输反代终止 TLS
如果继续打，我会从这里进 ① 用 DNS rebinding 打 callback_url，绕过提交时校验； ② 上传海量小文件打磁盘（没有存储配额）； ③ 用合法 token 提交大量合法任务打配额边界（并发竞态下的配额扣减）； ④ 在 text 里塞极端 Unicode（组合字符 / RTL / 超长单行）看字形覆盖与行宽计算。
