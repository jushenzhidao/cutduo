一次第一性原理重算

原方案在技术选型上没有明显错误——MLT + FFmpeg 是对的，队列设计是对的，hwaccel 清单是对的。但它把 80% 的篇幅花在了已经被商品化的那一层，而在真正决定生死的地方只写了三行。这份文档做两件事：把「剪辑能力」还原成物理量重新算一遍，然后给出结合 BSK 后的落地顺序。

  1. 渲染不是壁垒，是自来水。阿里云 IMS 公开报价 1080P 剪辑 ¥0.06/分钟，你的直接成本算下来约 ¥0.049/分钟——按分钟卖，毛利 18%，还要自己扛 SLA。同理 Shotstack 已把价格做到 $0.05/分钟起。这条赛道不能再进去。
  2. 两个设计假设物理上站不住。「MLT XML 是唯一事实来源」会让引擎升级等于存量工程全废；「双端差异 ≤ 1 帧」我在你这台机器上实测，换编码器就有 43.4dB / VMAF 97.06 的差异，而偏移 1 帧的伤害（VMAF 72.91）比换编码器大 24 分——这个容差既达不到、又太宽松，逻辑自相矛盾。
  3. 支点在两端，不在中间。客户不会为了「更快的 1080p」换供应商，但会为了「素材不用先搬一遍、成片不用手动发五个平台」付钱。BSK（腾讯开源 BrowserSkill，MIT）正好补的是这两端，而且是现成的。

01把「剪辑能力」还原成物理量

先不问用什么框架，先问这个东西在物理上是什么、成本由什么决定。

一次剪辑渲染，物理上是一个纯函数：

f( 素材字节, 时间线描述, 输出规格 ) → 成片字节 // 它没有状态、没有随机性、可以任意重放。这一点决定了后面所有设计。

商业上客户买的不是这个 f。客户买三件事：我不用自己写 f（省工程）、我敢直接用结果（省返工）、素材不用先搬家、成片不用手动搬回去（省运营）。把总成本拆到不可再分，只有五项：

成本项随什么增长优化上限现在谁在赚占原方案篇幅
C_render 算力输出分钟（纯线性）3–5×阿里云 IMS ¥0.06/min~70%
C_io 带宽 / 存储输出分钟（纯线性）2–3×云厂商~10%
C_correct 正确性失败次数（阶跃）10×没人做~5%
C_express 模板 / 表达模板数（可摊薄）∞没人做~5%
C_access 取材 / 分发客户数（可复用）10×没人做~0%
第一性结论 只有 C_express 和 C_access 有杠杆——它们随复用摊薄、随客户沉淀。C_render 是纯线性且已被卖成白菜价，优化它只能换来「更便宜的白菜」。原方案的阶段二（全面 hwaccel、3× 实时）优化的正是这一项。

定价的第一性原理：比较组决定毛利

同一支片子，客户拿它跟什么比，决定了你能收多少钱。这不是营销话术，是算术：

客户把它归到哪一类锚点单价你被压到的毛利结果
云转码 / 渲染 API¥0.06 / 分钟≈ 18%打不赢，也没有意义
外包剪辑师¥150–500 / 条≈ 99%有空间
运营 / 剪辑岗位人力¥8k–15k / 人月≈ 95%有空间（卖席位）

所以计量单位必须先改。一旦按「分钟」计价，客户会立刻把你放回第一个比较组，而你的成本结构（详见第 06 节）根本撑不住那个比较组。改成按「条」或按「席位」，同样的成本结构立刻变成 99% 毛利。

02实测：为什么「≤1 帧」必须废掉

原方案第 5 节把「同工程本地/云端渲染差异 ≤ 1 帧」写成验收指标。我在你的机器上跑了四组对照，用真实数字说明这个指标既达不到、又太宽松。

实验条件：同一条 IR（1080×1920、30fps、450 帧、3 段素材 + 中文标题层 + 音乐轨），同一台 Mac，只改一个变量。脚本在 cutproof/cutproof.py，可重跑。

M1 同后端渲染两次libx264 → libx264，只重跑一次
1.00000SSIM · 字节完全相同
M2 同 IR · 软编 vs 硬编libx264 vs VideoToolbox
99.44%SSIM · PSNR 43.4dB · VMAF 97.06
M3 同 IR · 时间线偏移 1 帧素材入点 +1，片长不变
96.08%SSIM · PSNR 25.4dB · VMAF 72.91
M4 字体缺失 · 错片渲染"成功"，中文全成豆腐块
97.97%SSIM · PSNR 24.3dB · VMAF 39.00

四条读数，每一条都在否定原合约

① L1 结构层对四种情况全部「通过」。四支片子的分辨率、帧数、fps、像素格式、色彩标记、音频采样率完全一致——包括那支中文全是豆腐块的错片。也就是说：「差异 ≤ 1 帧」这种结构级验收，等于什么都没验。

② SSIM 给错片打了 0.9797。一个看起来「很好」的分数，对应一支绝对不能交付的片子。原因很朴素：文字只占画面约 3% 面积，逐像素平均会把小面积高对比错误摊薄。

③ VMAF 抓到了（39.00），但 VMAF 需要 reference。这是关键限制：冷启动时你没有 reference——第一次渲染某个新模板时，谁知道「应该长什么样」？所以 L2 感知指标只能做回归，不能做首次正确性判定。首次正确性只能来自 L3 语义断言。

④ 排序颠倒，逻辑自相矛盾。合规差异（换编码器）VMAF 97.06；严重错误（偏移 1 帧）VMAF 72.91。两者差 24 分，而原合约规定「不同编码器要做到 0 帧差、但允许 1 帧差」——把伤害更小的东西定为不合格，把伤害更大的东西定为合格。

替换后的合约 L1 结构层：同后端 → 字节级完全一致（M1 已证明可达）；跨后端 → 字段全等。
L2 感知层：只用于回归，对已冻结的基准片 VMAF ≥ 95。不用于首次验收。
L3 语义层：编译期 + 渲染后断言，唯一能判「首次对不对」的东西。例：模板每个字符必须在打包字体里有 glyph（缺失 → 硬失败 E_FONT_MISSING）；文本包围盒必须落在安全区内；整片响度 -14 LUFS ±0.5。

这三层在 harness 里都已实现：L3 里的「字形覆盖率」和「安全区包围盒」是在编译期算的，不用等渲染——这是它相对 VMAF 的最大优势，也是它便宜的原因。

03IR 是事实来源，MLT XML 是编译产物

原方案第 2 节写「时间线工程（MLT XML）是唯一事实来源」。这一句会让后面所有能力被锁死。

意图（自然语言 / 参数 / 页面上下文） ↓ 编译（这是产品壁垒，也是安全边界） IR ← 事实来源：整数帧、内容寻址素材、引擎无关、可版本化 ↓ 编译（可缓存，key = hash(IR + 引擎版本 + 字体集 + 输出规格)） 执行计划：MLT XML / FFmpeg filtergraph ← 字节码，随时可换、可丢、可重编 ↓ 渲染

为什么 MLT XML 不能当事实来源：四条具体后果

① 引擎升级等于存量工程全废。MLT XML 里是 producer id、mlt_service 名、绝对帧号、文件路径、profile 名。这些是执行细节。Shotcut 大版本升级历史上就破坏过工程兼容性——一旦客户的模板是这个格式，你永远不能升级引擎。

② 缓存键不稳定。同一条逻辑时间线，两次生成可能得到不同文本（id 顺序、属性顺序、路径写法）。你没法用「这个工程渲过没有」来判断，缓存命中率做不上去，成本直接翻倍。

③ 无法跨引擎对账。你没法回答「MLT 渲的和 FFmpeg 渲的是不是同一支片子」——因为没有共同的输入可比。跨端一致性讨论就无从落地。

④ Agent 改 XML = 直接改执行计划。原方案说「意图编译层是安全边界」，但如果事实来源本身就是执行计划，Agent 只要拿到工程文件就等于拿到任意 mlt_service 注入面。

已实现 同一份 IR（ir/sample_15s_vertical.json）在本 harness 里编出了两个后端：MLT XML（out/timeline.mlt，结构校验通过）与 FFmpeg filtergraph（实际渲染出片）。IR 里没有一个字段提及 MLT。这就是「可换引擎」的具体含义。

IR 的四条硬约束（只写能落地的）

约束为什么必须这样
时间用整数帧浮点秒在 29.97 / 23.976 下必然累积漂移，且不同引擎取整规则不同。一漂就是 1 帧，而 M3 已经证明 1 帧错的代价远高于换编码器。
素材 sha256 寻址路径会变、会失效、会同名不同内容。内容寻址才能做去重、缓存、以及「这条成片到底用了哪个版本的素材」的审计。
文本先栅格化成图层一旦让渲染器在目标机现算字形，输出就绑定了那台机器的 freetype 版本和字体搜索路径，跨端一致从物理上不可保证。本例中标题层是先烘成 RGBA PNG、hash 进缓存键，渲染器只做合成。
不可表达即报错编译器遇到空洞轨道、不支持的 fit 模式时直接 E_IR_UNSUPPORTED，不允许静默降级成「看起来渲染成功了」。

04BSK：把支点挪到素材进 / 成片出

Tencent/BrowserSkill（MIT）：bsk CLI + 本地 daemon + Chrome/Edge 扩展，让 Agent 借用用户已登录的真实浏览器，在独立的 Agent Window 里干活，验证码和二次确认可以交还给人。

剪辑能力在物理上有三段路径。原方案只有中间那段：

BSK 覆盖
Path A

素材进得来

素材在客户的企业网盘、飞书、微信、创作中心草稿箱、内部 DAM 里——不在你的 OSS 里。需要登录、需要分页、需要断点续传。

已商品化
Path B

时间线变成像素

渲染。MLT + FFmpeg 是对的选择，但它是白菜：¥0.06/分钟，且已经有人替你扛完了合规、SLA、机房。

BSK 覆盖
Path C

成片发得出去

一条片子要变五个平台的规格、五个账号的草稿箱。发布必须人工确认，平台 DOM 会变，验证码会弹。

阿里云 IMS 的剪辑 API 要求素材已经在 OSS 上——这就是它拿不下「素材散落在客户内部系统」这类客户的真实原因，而不是渲染质量或价格。反过来，一旦你解决了 A 和 C，中间的 B 用谁的都不重要了。

3.1 顺带解决了「浏览器插件形态」的难题

如果自研 MV3 插件，你会被三条硬约束吃掉大部分工时（这些是平台规则，不是工程问题）：

MV3 约束对你的直接影响
禁止远程代码所有 JS/WASM 必须打包进插件。ffmpeg.wasm 不能 CDN 动态加载，得把 25–32MB 塞进包体，还要在 CSP 里声明 'wasm-unsafe-eval'（MV3 唯一允许的放宽，且商店会追问你为什么需要）。
SW 无 DOM、不能 new Worker()Service Worker 约 30 秒空闲就被终止，且不能创建 Dedicated Worker。所有重活必须走 chrome.offscreen（reasons:["WORKERS"]）再起 Worker，一个扩展同时只能有一个 offscreen document。
content script 受宿主 CSP 约束同一段代码在扩展页能跑、注入到站点页面就被拦。WebAssembly 在 content script 里还可能被页面策略限制。

用 BSK 则完全绕开：浏览器侧只负责「读页面 / 点按钮 / 传文件」，重活留在云端和本地 daemon，MV3 的坑由上游维护。你买到的是别人已经踩完的两年。

必须写进方案的边界（否则第二个月炸） 它不是渲染器。BSK 只搬字节、点按钮，不碰转码合成。
只适用客户端形态。纯 API 客户没有浏览器，仍需直传——两条链路都要有。
合规三原则：只操作客户自己授权的账号；发布必须人工确认；不做去水印、搬运、批量刷量。平台 ToS 与《反不正当竞争法》是硬红线，不是「注意事项」。
上游风险：daemon + 商店分发是供应链依赖。MIT 且 CLI/扩展源码可本地构建是唯一缓解——方案里要明确写「若上游停更，最小可自持部分是哪几个 crate / 哪个目录」。

05重排后的落地路线

原则：每个阶段有硬 Gate，不达标就停在那一步修，不许往下扩。阶段划分的依据不是「技术难度」，是「什么时候能签第一单」。

P0立合约（不写渲染代码）第 1–2 周

产物：IR schema v0、20 条「丑素材」语料、三层断言合约、失败分类学 v0。

丑素材必须包括：iPhone HLG HDR、VFR 手机视频、带旋转元数据的 MOV、10bit HEVC、无音轨、44.1k/48k 混合、0 字节、4 小时长素材、竖屏横拍、屏幕录制杂色。

  • Gate：21/21 分类正确（直通 / 归一化 / 拒绝三类都归对），归一化产物通过 8 项规格校验
  • 已交付：21 条语料 + 归一化引擎 + 矩阵，见同目录《P0 · 输入归一化手册》。1 条零转码直通、17 条转码通过、3 条按预期拒绝入队。
  • 没过这个 Gate，不许装 melt。输入归一化不解决，后面每个 bug 都会伪装成渲染 bug。
P1一条端到端链路（首个可售卖物）第 3–8 周

BSK 取材 → IR → 单机 melt/ffmpeg 渲染 → BSK 回传 → receipt。1 个模板、1 个平台、1 个真实客户。

为什么不是先搭农场：农场让你有「更快的 1080p」——一个卖不出价的东西；链路让你有「客户零迁移成本」——一个能签单的东西。

  • Gate：端到端 p50 ≤ 3 分钟（含取材与回传）；L3 断言 100% 通过；失败率 < 5%
  • Gate：同一 IR 渲两次字节级一致（M1 已证明这条可达，做不到就是你有非确定性因素没排干净）
P2生产化第 9–16 周

拉取式 worker 池（BRPOPLPUSH + 心跳巡检）、失败分类处理、幂等键、租户配额、操作审计（对上 BSK 的 audit 日志）。

同时开一条模板生产流水线：设计师出稿 → IR → 视觉回归 CI。这是真正的产能瓶颈，不是渲染。

  • Gate：7 天 soak，失败率 < 2%，实测单条成本（不是估算），模板从设计稿到上线 ≤ 3 天
P3按触发条件扩，不按时间表扩第 4–6 月
  • 上 hwaccel：GPU 排队时间 > 渲染时间的 30%
  • 上 K8s：单机池 > 3 台，或 > 5000 jobs/天
  • 开第二个模板族 / 第二个平台：首个客户月成片 > 500 条
  • 评估自研引擎：MLT 合成耗时占端到端 > 60%，且已优化到极限

GPU 采购规格必须写死为 L4 / L40S / T4。GeForce 卡在驱动层限制并发编码会话数（RTX 5090 三个编码引擎、全系统上限 12 路；RTX 4060 只有一个引擎），超限报错是 OpenEncodeSessionEx failed: out of memory (10)——看起来像显存不足，实际是许可上限。原方案「农场统一 NVIDIA 最稳」这句话没错，但漏了这个，采购单会直接锁死并发。

07失败分类学

商业化的 80% 在这里，而原方案一个字没提。失败分类学的价值不在于「记录错误」，在于把不可控变成可控。

错误码检出点可重试客户可见文案
E_INPUT_UNREADABLE入库 ffprobe否素材无法解析（编码或封装不支持），已列出探测到的实际格式
E_INPUT_VFR入库否素材为可变帧率，已自动转为恒定 30fps（时长误差 0 帧）
E_INPUT_HDR入库否素材为 HDR（HLG/PQ），已按 BT.709 SDR 转换交付
E_INPUT_ROTATION入库否已按显示矩阵旋转校正（原始 1920×1080 → 校正后 1080×1920）
E_MEDIA_MISSING编译否引用的素材不存在或已过期，附 asset id
E_IR_INVALID编译否时间线参数非法：字段名 + 实际值 + 允许范围（Agent 要能据此自动修正）
E_FONT_MISSING编译预检否硬失败。模板字体缺失，禁止静默替换。附缺失字符码点列表
E_TIMEOUT执行是渲染超时，已按降预设自动重试一次
E_OOM执行是资源不足，已降并发重排
E_NVENC_SESSION执行是编码资源繁忙（会话上限），已退回 CPU 路径
E_OUTPUT_INVALID交付前校验是成片校验未通过（L1/L3 断言失败），已自动重渲
E_PUBLISH_FAILEDBSK 投递视情况发布失败：需要人工确认 / 需要重新登录 / 平台页面结构变更
一条铁律 E_FONT_MISSING 必须硬失败。字体静默回退是商业化最典型的「看起来成功、成片是错的」事故——M4 那支豆腐块片子，渲染进程退出码是 0，文件大小正常，SSIM 0.98，如果不做编译期字形覆盖检查，它会一路走到客户手里。

另一条：所有错误码的文案必须对 Agent 可执行。原方案说「编译失败即返回结构化错误，Agent 可自动修正重试」，这句话要成立的前提是错误信息里带字段名、实际值、允许值三件套——否则 LLM 只能瞎猜重试，烧的是你的 GPU 配额。

08本周七天

不需要立项、不需要排期，七天能全部做完。做完之后你会有足够依据去改这份方案。

1
用真实报价单重算定价模型阿里云 IMS 剪辑价 + Shotstack 各档 + 你自己的 spot 单价。把「卖分钟 / 卖条 / 卖席位」三个方案的毛利算出来摆在一张纸上，然后选一个。这一步不写代码，但决定后面所有事。
2
20 条丑素材跑 ffprobe，写归一化矩阵这一步的产出直接决定后面所有工期的可信度。凡是没做过这一步的渲染项目，工期都会翻倍。
3
把三层断言接进 CIcutproof/ 可以直接用：M1 守确定性，L1 守结构，L3 守正确性。红灯即阻断合并。
4
IR schema v0 定稿，MLT XML 降级为编译产物同时把「时间用整数帧」「素材 sha256」「文本先栅格化」三条写进 schema 注释，它们是不可逆决定。
5
MCP 契约改成证据型现在返回 {status, url}；改成返回 receipt（结构 JSON + 首尾帧 + contact sheet + 响度 + 断言结果）。Agent 看不见视频，你只给它 URL 它就只会瞎试。
6
GPU 采购规格改成 L4 / L40S / T4并把驱动版本 + nv-codec-headers 版本锁进镜像。升驱动导致编码崩、且代码一行没改——这是 NVENC 最常见的事故。
7
用 BSK 手工跑通一次「取材 → 渲染 → 回传」不写自动化，就手工。全程录屏。这一小时的录屏比十页架构图更能说服客户和投资人——它证明「素材根本不用搬家」这件事是真的。

关于文中的实测数据：来自本机 cutproof/cutproof.py（macOS / Apple Silicon / ffmpeg 9.0.2 / 1080×1920 / 30fps / 450 帧）。原始输出在 cutproof/out/measurements.json，可 python3 cutproof.py all 重跑复现。MLT 分支只做了结构校验（本机无 melt 运行时），因此 M2 用的是同机双编码器而非跨引擎对照——但它已经足够证明「跨后端不可能字节一致」这一点。

关于 BSK：Tencent/BrowserSkill，MIT。文中关于其能力的描述基于公开仓库与文档（借 tab、Agent Window 隔离、human-in-loop、0.3.x 的远程配对与操作审计）。文中关于 MV3 的三条约束基于 Chrome 扩展平台规则，与 BSK 无关——列出来是为了说明「为什么不自己写插件」。
