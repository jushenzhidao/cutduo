# 蒸馏方法论 · 把一个外部技能变成自己的规则

> 目标不是「把别人的东西搬进来」，而是**用最小代价拿到能复用的模型，并留下可验证的痕迹**。
> 一次吸收的完成态是：**一份分析文档 + 至少一个可运行产物 + 一条登记**。
> 登记表：[`distillations.json`](distillations.json)；自动索引：[`蒸馏-索引.md`](蒸馏-索引.md)。

## 0. 先定性：它到底是什么

同一个仓库里可能混着三种东西，处理方式完全不同。先看证据，再下判断：

| 类型 | 判据（实测） | 能借什么 | 不能借什么 |
|---|---|---|---|
| **引擎** | 有渲染循环 / canvas / WebGL / 宿主入口；文件数多、依赖重 | 渲染机制、时间轴模型（重写） | 整仓代码、构建链 |
| **方法包** | 主要是 Markdown / JSON / 规则表；代码很少 | 内容模型、字段契约、节奏规则 | 它的视觉实现（往往只是示例） |
| **素材包** | 图片 / 音频 / 字体 / 模板包为主 | 素材清单、命名与出处 | 把素材当代码能力 |
| **混合** | 引擎 + 方法 + 素材 | 分开处理，不要一刀切 | 用「整体评估」代替分层判断 |

**证据优先**：包大小、文件数、入口文件、许可证、是否有 `render` / `main` / `stage`、
内容是不是 JSON 驱动的。不要根据 README 的自我描述定性——README 通常把方法包写成引擎。

## 0.5 先用计划器跑一遍只读分类

```bash
node tools/intake.mjs plan --source <目录或 .motion 文件> --json
```

它输出定性、建议深度、保护/凭据/许可阻塞与 `distill-inspect` 报告；确认分类后再进入下面的判据与落地。
计划器不会执行模板代码、不解包 ZIP、不写 `kits/` / `api/` / `templates/`。

## 1. 判据过筛：两条硬门槛

在决定「换宿主 / 半蒸馏 / 全蒸馏」之前，先过这两条：

1. **宿主能力**：引擎必须是 Canvas2D（有 `src/dom.js` 或大量 `createElement('div')` ⇒ 换宿主等于写半个浏览器）。
2. **源码可读**：`protection: protected` / AES 密文 ⇒ 只能 Chrome 或照片反推；蒸馏仍可做，但要重写渲染。

> **许可 / 协议（2026-11-15 用户指令）**：不作为工具阻断项。`tools/intake.mjs` 只在 evidence
> 里记录 LICENSE 文件，不再产生 `LICENSE_MISSING` / `LICENSE_RESTRICTED` 告警；是否可分发、
> 是否需要署名由使用者自行判断。工具不会删除源里的 LICENSE / NOTICE 文件，也不伪造作者。

> 换宿主不是性能手段。它省的是 Chromium 依赖与可定制性，不是时间。
> 速度只有两处能白拿：关掉模板自带的 QA/记账链路、重复绘制缓存。

## 2. 三条必须实测的「不可平移假设」

这三条在多个上游项目上重复出现，**不要从上游文档照抄数值**：

| 假设 | 上游常见值 | 为什么不能平移 | 本仓做法 |
|---|---|---|---|
| **帧率基线** | 按 0.1s 采样 / 逐帧差分 | 差分随帧率线性变小，时间基线错 6 倍 | 先 `ffprobe` 读真实 fps，再算阈值 |
| **底色极性** | `lum > 120` 取前景 | `paper` 的浅底会把整张纸当主体 | 先判底色极性，再取前景；负向用例验证 |
| **版式家族阈值** | 一个「静止 ≤3s」管所有版式 | 不同家族静止占比差 15 倍 | 按版式分家族标定；只报不拦 |

结论写成「可平移的规则」与「不可平移的假设」两栏。**不可平移的部分要写清为什么**，
否则下一个人会再试一遍。

## 3. 落到哪里

| 产出 | 落点 | 要求 |
|---|---|---|
| 分析文档 | `docs/<名>-蒸馏-<日期>.md` | 定性、判据、可平移/不可平移、对抗审查 |
| 版式 / 段型 | `kits/<id>/` + `api/kits/<id>.mjs` | 文件名 = id；跑 `npm run inv` |
| 三件套模板 | `templates/own/<id>/` | `kit.js` + `layouts.js` + `stage.js` |
| 检查工具 | `tools/check-*.mjs` / `tools/*-check.mjs` | 能独立运行，有负向用例 |
| vendor 源码参考 | `node tools/intake-copy.mjs --plan ... --yes` | 默认落 `refs/replicas/<id>/vendor-source`；保留 LICENSE、排除凭据；**不是可直出模板** |
| 规则 / 判据 | `src/gate.mjs`、`src/temporal.mjs`、`tools/knowledge/` | 先只报不拦，标定后再拦 |
| 登记 | `docs/distillations.json` | `status` + `doc` + `artifacts` |

**不整仓拷贝**。上游的 `package.json`、构建脚本、示例素材、CI 一律不进本仓；
只取能解释清楚的规则与数据。

机械动作可用 `node tools/intake-apply.mjs --plan out/intake/<id>/plan.json`：
rehost 生成 adapter，semi/full 生成骨架；默认 dry-run，`--yes` 才写。**画面语言仍要人写。**

## 4. 对抗审查：至少一条负向用例

任何新判据 / 检查工具，交付前必须回答：

1. **假阳性**：健康片会不会被判 FAIL？拿 3–5 支现有成片跑一遍。
2. **假阴性**：故意造一个坏样本（插黑场 / 截短音轨 / 删一个字 / 越界时刻），能不能拦住？
3. **自身失效**：检查器没输出时，是 PASS 还是 FAIL？（必须是 FAIL，不能是「跳过」）
4. **口径漂移**：阈值是从上游抄的，还是在本仓分布上标定的？写清样本量与误杀数。

历史教训：`hook ≥0.5` 误杀 13/19；`静止 ≤3s` 误杀 12/26；60fps 片用 30fps 切帧导致
8/8 报「重复帧」。**上游的线是它自己片子上的分布，不是普适定律。**

## 5. 登记（必做）

在 `docs/distillations.json` 里加一条：

```json
{
  "id": "upstream-name",
  "date": "YYYY-MM-DD",
  "upstream": "作者/仓库 或 skill 名",
  "kind": "engine | method | assets | mixed",
  "depth": "original | rehost | semi | full | rules",
  "status": "landed | partial | assessed | rejected",
  "verdict": "一句话结论：吸收了什么、放弃了什么、为什么",
  "doc": "docs/<名>-蒸馏-<日期>.md",
  "artifacts": ["kits/<id>", "api/kits/<id>.mjs", "tools/check-x.mjs"]
}
```

然后：

```bash
npm run distill:md      # 生成 docs/蒸馏-索引.md
npm run distill:check   # 校验：doc/artifact 是否存在，状态与产物是否矛盾
npm run check           # 全量：出帧冒烟 + 文档漂移 + 蒸馏索引
```

**状态与产物必须一致**：`landed` / `partial` 必须有产物；`assessed` / `rejected` 允许空。
`artifacts` 里至少有一个能运行/能渲染的东西（代码文件或目录），否则「落地」不成立。
