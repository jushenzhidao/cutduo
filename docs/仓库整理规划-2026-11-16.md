## 一、结论

**问题不在目录摆放，在门禁测错了对象。**

仓库已经在 2026-11-13 做过一次平铺重构（见 `templates/README.md` 末段、`README.md` §目录），
目录层面没有明显病灶。真正的缺口是三条：**契约层声称的唯一性不成立、13 个调用方绕过门、
15 项自检全绿却测不到架构走样**。

三组硬数字支撑这个判断：

| 观察 | 实测 | 含义 |
|---|---|---|
| 契约层比它包装的实现还长 | `api/` 2009 行 / 19 文件 | 2K 行全是 `spawn` 适配，不含业务逻辑 |
| 真正的统一管道极薄 | `src/pipeline.mjs` **127 行** | 帧循环/编码/封装早已统一 |
| 绕门调用方 | **13 个文件** | API-first 的定义是没有第二条路 |
| 自检可信度 | `docs:check` 15/15 PASS | 它测的是"文档与清单一致"，不是"架构未走样" |

最尖锐的一处自相矛盾在同一个文件里：

- `docs/API.md:204` 写 `api/index.mjs ← 唯一的业务实现`
- `docs/API.md:225` 写 `各支走子进程…把 _runner.mjs 的 spawn 换成 import 即可`

如果 api 是唯一实现，就不该 spawn 去调外部脚本；既然 spawn 了，实现就不在 api 里。这两句必须改掉一句。

## 二、第一性原理分解

这个仓库只产出一样东西：**MP4**。剥到最小，它就是一个函数

```
f(params: JSON) → mp4
```

其余一切按"对 f 的角色"归类，只有四种，互斥：

| 角色 | 定义 | 判据 | 变更速率 |
|---|---|---|---|
| **1 实现** | 把 params 变成帧、变成字节 | 出现在 f 的调用链上 | 慢（按月） |
| **2 契约** | 描述 f 接受什么、返回什么 | 可从 f 生成或对 f 校验 | 慢（按版本） |
| **3 宿主** | 让人/程序能调用 f | 只依赖角色 2，不依赖角色 1 | 快（按需） |
| **4 输入/证据** | f 的原料与产物 | 不进 f 的调用链 | 每支片都变 |

### 现状：角色混淆点

| 位置 | 自称角色 | 实际角色 | 证据 |
|---|---|---|---|
| `api/**` | 1 实现 | **3 宿主** | 11 个 kit 文件全部 `cliAdapter` → `spawn(node script)` |
| `tools/` 13 个脚本 | 3 宿主 | **3 宿主但直连 1** | 绕过 `api/` 直接 spawn `render.mjs` |
| `kits/editorial/canvas-editorial.mjs` | 1 实现 | **1 实现（第二份）** | 893 行，自带 `new Worker`×2 / `encodeRange` / `mixAudio`，**未 import `src/pipeline.mjs`** |
| `deliverables/` | — | 4 证据 **混 5 交付记录** | 59 tracked：mp3 / zip / mp4 / html / md 混放 |
| `packages/` | — | **无角色（孤儿）** | 2 个 `.motion`，不在任何文档目录表、不进 `inventory` |

`packages/` 是最干净的一个信号：一个目录只要不属于任何角色，就没人知道该不该动它，
于是它永远停在那里。这类"无主目录"是整理的第一优先清理对象。

## 四、分期方案

排序依据是「**回归风险 × 事实错误持续误导的成本**」，不是"先易后难"。

### P0 · 修事实（半天 / 零回归风险）

这一期的价值不是整理，是**停止用错误陈述误导后续开发（含 AI 读取 AGENTS.md 之后的每一次会话）**。

| 动作 | 文件 | 改法 |
|---|---|---|
| P0-1 | `AGENTS.md` §3 硬规则 1 | 「`api/` 是唯一业务实现」→「`api/` 是唯一**对外契约层**；渲染实现在 `src/pipeline.mjs` + `kits/*/`，各 kit 走子进程是为了隔离，不代表 api 是实现在地」 |
| P0-2 | `docs/API.md:204` + `:225` | 两句合并为一段，消除自相矛盾；`api/index.mjs` 的标注改为「唯一对外契约入口」 |
| P0-3 | 新增 `tools/check-arch.mjs` | 量 I1 / I2 / I3，输出 PASS/FAIL 明细；接入 `npm run check`，**先只报不拦** |
| P0-4 | `packages/` | 2 个 `.motion` 移到 `templates/fixtures/`（或补进 `README.md` 目录表并进 `inventory`）。**二选一，不留无主目录** |

**验收**：`npm run check` 输出新增 arch 段；`grep -rn "唯一业务实现" --include=*.md` 为 0。

### P1 · 收口入口外壳（1–2 天 / 中风险）

关键澄清：**管道不需要重构，入口外壳才需要**。4 个入口已经共用 `src/pipeline.mjs` 的
`planShards / partArgs / pumpFrames / spawnPart / concatParts`，重复的只是外壳
（parseArgs → 默认值 → 参数校验 → 注册字体 → 调管道）。

| 动作 | 内容 |
|---|---|
| 抽 `src/entry-kit.mjs` | 一个 `runKitCli({ kitName, rendererFactory, schemaPath })`：解析 argv、读 params、套默认值、注册字体、调 `src/pipeline.mjs`、打回执 |
| 四个入口降为适配器 | `render.mjs` 330→~60、`desk` 177→~35、`mg` 131→~30、`diagram` 306→~60（它保留独立的帧循环但统一外层） |
| 删冗余 | 删 `kits/desk/render.mjs:23` 与 `kits/mg/render.mjs:27` 的 `resolveInput`，改 import `src/root.mjs` |

**为什么值得做**：不是为了少几行代码，是为了让**默认值只有一处**。现在 4 份外壳各自决定
fps / crf / workers / preset 的默认值，任何一处改了，另外三处就是隐性不一致，而
`overrides` 白名单又假定默认值统一（`AGENTS.md` §1）。

**验收（必须逐项过）**：

1. `npm run det:all` 全绿（确定性）
2. 逐 kit 出片对比：帧数 / 时长 / 首帧 pHash 三项与改造前一致
3. `npm run api:cap:check` + `npm run inv:check` + `npm run docs:check` 全绿
4. 入口合计行数 944（不含 editorial）→ ≤200

**回滚**：按 kit 逐个改、逐个提交。任一 kit 出片不一致，只回退该 kit。

### P2 · 合门（2–3 天 / 中风险，收益最大）

13 个绕门文件按"是否真的出片"分两组，**不能一刀切**：

| 组 | 文件 | 改法 |
|---|---|---|
| **A 出片路径**（5） | `web/pipeline.mjs`、`harness/run.mjs`、`tools/render-all.mjs`、`tools/new-film.mjs`、`tools/contact-sheet.mjs` | 改 `import * as api from '../api/index.mjs'`，走 `render()`；`overrides` 只放超参 |
| **B 元数据路径**（8） | `tools/inventory.mjs`、`check-kit-contract.mjs`、`intake-apply.mjs`、`intake-copy.mjs`、`verify-calibration.mjs`、`motion-render.mjs`、`knowledge/new.mjs`、`knowledge/knowledge.mjs` | 它们要读源码结构，不该 spawn CLI。改 `import { registry } from '../api/registry.mjs'` 取元数据；确需渲染时走 A 组同一接口 |
| **C bench 豁免** | `bench/**`、`kits/desk/tools/bench-*.mjs`、`kits/diagram/sheet.mjs` | 明确写入 `check-arch.mjs` 白名单，理由：bench 的目的是测底层性能，绕门是**合理**的，拦掉会让探针失真 |

> A/B 分组按文件内容初判，落地前需逐个确认（`grep` 计数无法区分"路径字符串"与"真调用"）。

**验收**：`check-arch` 的 I2 计数从 13 → 0（白名单外）；`npm run check` 全绿；
任取一支片用 `web` 界面与 CLI 出片，产物 `ffprobe` 三项一致。

### P3 · editorial 归一（2–3 天 / 高风险，可选）

`kits/editorial/canvas-editorial.mjs` 893 行是唯一真正的第二实现：自带 `new Worker`×2、
`encodeRange`、`mixAudio`，完全不走 `src/pipeline.mjs`。

**建议只在有实际收益时做**：例如需要它支持 `overrides.fps/workers`，或需要它进 `web` 自助台。
纯粹为了整齐去改 893 行高风险代码，收益不成立。

若要做，路径是：先让它 `import` `src/pipeline.mjs` 的 `concatParts` / `pumpFrames`，
保留自己的 `renderFrame` 与缓存策略；分两步提交，每步 `npm run det:all` 验证。

## 六、明确不做的事（对本方案的自我反驳）

整理方案最容易犯的错是"为了整齐而增加风险"。以下五条经审查后判定**不该做**：

1. **不合并 `kits/` 进 `src/`**
   `kits/` 20601 行（99 文件）是内容与版式，`src/` 2686 行（12 文件）是管道，变更速率差约 8 倍。
   合并会让"改管道"的 diff 与"改版式"的 diff 混在一起，review 与回滚粒度同时变差。

2. **不改 `templates/` 四层目录（`01-original` ～ `04-full-distill`）**
   `templates/README.md` 已给出论证：这四层表达"接入深度"，是**过程属性**，会随投入变化；
   按它搬文件会让路径天天变。该文件末段明确写了"路径稳定性优先于整齐"。这是已决策，重开无收益。
   同理不动 `own/` 与 `vendor/` 的分法（按"能否分发"分，属许可硬约束）。

3. **不统一 5 处 `new Worker`**
   `src/pipeline.mjs:9` 的注释已说明原因：`new Worker(new URL(import.meta.url))` 必须由入口
   自己写，worker 要指回自身文件。强行抽成公共函数会破坏这个指向。**这是有意为之，不是遗漏。**

4. **不为整齐重排 `tools/` 73 个脚本**
   路径被 15 项 `docs:check` 与 78 个脚本引用交叉绑定，改名的收益远低于破坏面。
   `tools/` 真正需要的是**分类标注**（生产 / 元数据 / bench），不是搬家。

5. **不删 `deliverables/` 里的已交付件**
   含 mp4 / zip / mp3，删了不可重建（不是 `out/` 那种可再生成的产物）。
   只建议：**此后新增的中间产物不再进 `deliverables/`**，它应只保留对外交付记录。

## 七、门禁设计（为什么现有 15 项抓不到）

现有检查的性质必须说清：

| 检查 | 测什么 | 抓不到什么 |
|---|---|---|
| `docs:check` 15 项 | 文档里的数量/路径/覆盖与清单一致 | 新增第二个渲染入口；调用方绕过 API |
| `inv:check` | `inventory.json` 与磁盘一致 | 同上 |
| `kit:check` 8/8 | 渲染器认的段型 vs schema 允许的段型 | 同上 |

三个检查器共享"清单"，但**清单本身不记录架构不变量**。所以它们能抓"新增 kit 没写进 README"，
抓不到"新增 kit 时顺手又写了一套 `new Worker` + `ffmpeg` 管道"。

`check-arch.mjs` 要补的正是后者。设计要点：

1. **I2 用"路径出现"而非"进程调用"判别**：`grep -l 'render\.mjs'` 简单可靠，
   漏报（注释里提到）由白名单显式列出处理，不追求零误报。
2. **必须带负向自检**：脚本内置 `--self-test`，临时造一个违反 I1 的文件，断言检查器能报错退出非零。
   报错就说检查器失效。这是 2026-11-14 `adversarial.mjs` 报 8/8 假"重复帧"的教训——
   **审查自身也会错**。
3. **先只报不拦**：新指标上线第一周只输出不失败，确认误报率后加 `--strict`。
   参照 `src/gate.mjs` 的经验：hook / 亮度 / 重复帧这类只能报，完整性类才能拦。

## 九、执行结果（2026-11-16 当日完成）

P0 / P1 / P2 已按本方案落地；P3（editorial）按建议保留为长期豁免。
验证方式不是「自检绿了」，而是**逐支对比改造前后的成片指纹**（帧数 / 时长 / 分辨率 / 抽帧 md5）。

### 9.1 基线不是可选项

改造前先出四支片并冻结指纹（`out/arch/baseline.json`）：paper 2573 帧 / desk 3420 / mg 1920 / diagram 780。
改完逐支重渲、逐帧比对。**这一步拦下了一个真实缺陷**：首次重构后 paper 体积从 0.91MB 变 0.93MB，
原因是 `renderPart` 漏传 `x264Threads`（worker 内 x264 退回默认线程数，码率控制变了）。
只差 2%，肉眼与门禁都看不出——没有基线就永远发现不了。

### 9.2 实际改动

| 期 | 动作 | 结果 |
|---|---|---|
| P0-1 | `AGENTS.md` 规则 1、`docs/API.md` 两处「唯一业务实现」 | 改为「唯一对外契约层」，并说明各支走子进程 ≠ api 是实现 |
| P0-2 | 新增 `tools/check-arch.mjs`（I1/I2/I3 + `--self-test`） | 已接入 `npm run check`（`--strict`）；`npm run arch` / `arch:selftest` |
| P0-3 | `packages/` 两个 `.motion` | 迁到 `out/packages/`（可重建）；`build-template.py` 默认输出同步改到 `out/packages/` |
| P1 | 新增 `src/entry-kit.mjs`；`render.mjs` / `desk` / `mg` 降为适配器 | 四入口 944 → 752 行；`resolveInput` 私有副本 2 → 0；`registerFonts` 四套 → 一套 |
| P2 | 5 个活宿主改走 `api/cli.mjs`；5 个断链文件移 `tools/legacy/` | I2 白名单外计数 13 → 0 |

### 9.3 与规划的偏差（必须记账）

1. **P1 没做到 ≤200 行，实际 752 行。** 原估算错在假设入口大部分是重复外壳。
   实测：四个入口共用 `src/pipeline.mjs` 早已成立，重复的只是 parseArgs / worker / concat / probe。
   抽走这些后剩的是**各支独有逻辑**——`kitSpec` 75 行（模板解析与报错话术）、`loadParams` 60 行
   （声明式时间 + snapToFrames + profile）、diagram 的 timeline 与 `renderFrame` 100+ 行。
   这些搬走只会制造新的间接层。**价值不在行数，在默认值从四份收敛到一份。**
2. **P2 原判 13 个绕门，实际只有 8 个是真的。** 5 个差额来自两类：
   - 2 个是误报（`contact-sheet.mjs` / `knowledge/*` 只在注释与提示字符串里提到 render.mjs）
   - 3 个是**断链死代码**（`render-daemon` / `render-parallel` / `build-voices*` / `test-theme`）：
     import `./canvas-editorial.mjs`（实际在 `kits/editorial/`）、依赖 `packages/editorial-sync.motion`
     （从未入库）。它们是 2026-11-13 平铺重构的未收尾。
3. **`template-smoke.py` 无法走 API**：它测的是任意模板目录，这些目录没有 kit id、未注册进 capabilities。
   这是契约覆盖面的真实边界，已写进豁免表而非硬改。

### 9.4 检查器的判据改了 3 次——这件事本身是结论

`check-arch.mjs` 的第一版几乎全错，逐版收紧：

| 版本 | 判据 | 结果 | 问题 |
|---|---|---|---|
| v1 | 全仓匹配 `libx264\|mpegts` | 报 19 个 | 注释、错误正则、`-c:v copy` 全算违规 |
| v2 | spawn + libx264 同时在场 | 报 8 个 | 仍把 reframe（后处理转码）、desk 探针算进去 |

### 9.7 门禁盲区：`api.render` 从未被自动验证（同日补）

清掉架构欠债后再查一遍「现有检查到底测了什么」，发现一处真盲区：

- `npm run check` 的 API 段全部走 `api.probe`，而 probe 在 `render.mjs` 里是 `process.exit(0)`
  **早退**——worker 分片、`concatParts` 合流、音轨混流这三段根本不执行。
- 「回执规格只信 ffprobe」是 `docs/API.md` 的硬承诺，但承诺本身从没被断言过：
  如果哪天 `contract.probeOutput` 改成读子进程自述，probe 全绿也发现不了。
- 所有 probe 都无音轨，`concatParts` 的「PCM → aac」分支（mp4 里塞 pcm 会让浏览器整轨静音）
  从未在自检里跑过。

补法：**一条检查覆盖三件事**，用 paper（2573 帧里最快的一支，约 6s）加一条现场合成的 3 秒 PCM wav：

```
PASS  api:render 端到端 回执 2573 帧 == ffprobe 2573 帧 · 音轨 pcm→aac
```

负向验证（两条都必须能红，否则是摆设）：

| 人造缺陷 | 期望 | 实测 |
|---|---|---|
| `contract.mjs` 的回执帧数 `+1` | 回执与 ffprobe 不符 | 回执 2574 vs ffprobe 2573 → FAIL |
| `concatParts` 的音轨策略改成永远 `-c:a copy` | 产物音轨不是 aac | `codec_name=pcm_s16le` → FAIL |

代价：`npm run check` 从 17s → 31s。换的是一条真正跑主流程的端到端。
