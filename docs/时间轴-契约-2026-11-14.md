# 时间轴契约（`src/temporal.mjs`，2026-11-14）

> 来源：`hypit-ai/hypit` 的 `packages/temporal` 四层模型（Narrative → Alignment → Projection → Instant/Window），
> 按本仓情况裁到后两层。**只借语义，未使用其代码**（其协议禁止商业再分发与多租户，见 `hypit-蒸馏-2026-11-14.md`）。

## 一、为什么要有这个文件

本仓按帧渲染，但 params 里的时间写成浮点秒（`t0: 12.433`）。三类问题此前没人管，一出就是成片上的可见错误：

| 问题 | 后果 |
|---|---|
| 窗口倒序或空（`t1 <= t0`） | 渲染器画出一段 0 帧镜头，静默跳过 |
| 边界不在帧上（`t1 × 60 = 1206.06`） | 逐帧取整后相邻镜头漏一帧或多一帧 |
| 相邻窗口重叠 | 后一个镜头抢走前一帧，转场闪一下 |

## 二、模型：两层，不是四层

```
hypit：Narrative → Alignment → Projection → Instant/Window
本仓：                                Window / Extent
```

语义层（哪句话、哪个论点）归内容侧（`tools/knowledge`、`content/*/script.json`），渲染器不该知道。本仓只需要：

- **Window**：绝对、半开 `[start, end)`、端点在帧边界；
- **Extent**：无位置的帧数（`segments[{dur}]` 累加时用）。

三条硬规则，**不裁剪、不修复、不推断**：

1. 半开区间必须非空（`end > start`）；
2. 窗口属于某条 Timeline（同一个 fps），越界即拒绝；
3. 相邻窗口取整后必须首尾相接。

## 三、判据标定：帧对齐为什么只告警

上游把"端点在帧边界"当硬约束——因为它的时间是作者直接声明的帧。**本仓的时间多数来自口播实测时长**（浮点秒），照搬的结果是：

```
v8t.json  → 30 条 FAIL，全部是 0.16–0.36 帧的偏差（3–6 ms）
```

这些偏差在 `Math.round(t × fps)` 时被吸收，肉眼不可察。**真正的风险不是"端点不整"，是"相邻窗口取整后不连续"**——那条用帧比较单独判：

```js
const pe = toFrame(prev.end, fps), cs = toFrame(cur.start, fps);
if (cs < pe) errors.push(`重叠 ${pe - cs} 帧`);
```

用帧比而不是秒比：用秒会因浮点误差放过真实的 1 帧错位，也会因 0.001 s 的重叠误报。

所以最终判据：

| 检查 | 级别 | 理由 |
|---|---|---|
| 空窗口 / 倒序 / 越界 | **FAIL** | 渲染结果一定错 |
| 取整后重叠 | **FAIL** | 成片上看得见 |
| 端点偏离帧边界 > 0.5 帧 | warn | 半帧以内取整即吸收 |
| 取整后空隙 > 0.5 s | warn | 多数是字幕间隙，信息性 |
| 未配音骨架（captions 全 0–1 s） | warn | 占位数据，配音后才定稿 |

## 四、声明式写法

三种，语义不同——**改哪个字段只影响它声明的那一端**：

| 写法 | 起点 | 末端 | 改时长时动谁 |
|---|---|---|---|
| `{from, for}` | 锚定 | 跟随 | 只改 `for` |
| `{until, for}` | 跟随 | 锚定 | 只改 `for` |
| `{from, until}` | 锚定 | 锚定 | 两个都要改 |

```js
import { declareWindow, makeTimeline } from './src/temporal.mjs';
const tl = makeTimeline({ fps: 60, durationSeconds: 105.65 });
const w = declareWindow({ from: 20.35, for: 6.0 }, tl, 'quant');
w.startFrame; // 1221
w.edit.note;  // '起点锚定；改时长只动 for，末端自动跟随'
```

## 七、顺手修掉的一个 bug

`tools/knowledge` 的 `buildSkeleton` 原先按**秒**分配每段时长（`toFixed(2)`），29 段累加后成 165.03 s，比声明的 165 s 多 1 帧——`segments[29]` 落到时间线外，最后一段被截。

改成按**帧**分配：整数分配后把余数按小数部分补给各拍，保证累加精确等于总帧数。拆段同样按帧、余数给前几段。

```js
const totalFrames = total * fps;
const frames = exact.map(Math.floor);
let rem = totalFrames - frames.reduce((a, b) => a + b, 0);
for (let k = 0; k < rem; k++) frames[byFrac[k % byFrac.length][1]]++;
```

**这是本轮校验器抓到的第一个真问题**——不是它写错了，是它暴露了别处写错。

## 八、声明式已接入渲染（2026-11-14 晚）

`loadParams` 现在先调 `normalizeTiming()`：把 `{from, for}` / `{until, for}` / `{from, until}` 展开成 `t0/t1`，**渲染器完全不用认识声明式**。校验与渲染共用同一套展开，不会出现"校验按声明算、渲染按绝对算"。

```json
{ "type": "number", "from": 20.35, "for": 15.12, "args": { ... } }
```

实测：把生日悖论前 4 段改成声明式，出片 6339 帧，与手写版逐帧比 —— **6323 帧完全一致，16 帧有差异**。

那 16 帧全部落在 `point` 段入场动画的前 0.3 秒：声明式展开时把起点归到整帧（12.6833 而非 12.68），动画相位晚 0.2 帧，而 eOut 曲线在起点斜率最大，所以单帧 PSNR 只有 21.8。**这是帧对齐的必然结果，不是错误。**

## 十、两个坑

**1. `from` 是内容字段，不只是时间字段。** `night-card` 的 quote 段就有：

```json
{ "type": "quote", "dur": 9, "text": "...", "from": "某个凌晨 · 03:47" }
```

这里的 `from` 是"出处"。宽松判断会把它当时间声明，报"声明不完整"并拦死整支片——**冒烟测试当场抓到 2 个 FAIL**。修法：`isTimeValue()` 只认数字或纯数字字符串，且 `dur` 优先于 `from/until`。

**2. 声明式窗口展开后落整帧。** `for: 12.43` 这类十进制在 `t0 + for` 时带 1e-4 级误差，个别帧边界会取整到相邻帧。展开时直接 `toSeconds(toFrame(...))`，让声明式窗口天然落在帧上。

## 十二、引用式顺移（2026-11-14 晚）

声明式只保证"窗口内"原子（改 `for` 起点不漂）。要让**后续窗口跟着动**，需要引用：

```json
{
  "scenes": [
    { "type": "hero",   "from": 0,              "for": 12.43 },
    { "type": "point",  "from": "@prev+0.25",   "for": 7.42  },
    { "type": "number", "from": "@prev+0.25",   "for": 15.12 }
  ],
  "durationSeconds": "@last+0.02"
}
```

支持 `@prev` / `@prev+N` / `@prev-N`（同数组顺序解析），以及 `durationSeconds` 的 `@last` / `@last+N`。

**实测**：9 段全链式，只改 `scenes[0].for` +2 秒 ——

```
scene[0] t0 0.00  → 0.00    (0s)
scene[1] t0 12.68 → 14.68   (+2s)
scene[2] t0 20.35 → 22.35   (+2s)
...
scene[8] t0 95.15 → 97.15   (+2s)
总时长 105.65 → 107.63（@last 自动跟随）
```

**改 1 个字段，9 段全部顺移，总时长跟着走。**

### 代价：帧对齐会累积亚帧偏移

链式版与手写版逐帧比：6339 帧里 **115 帧不同（1.8%）**，全部在各段入场动画的头几帧。

原因：`for: 12.43` 不是整帧（745.8 帧），展开时归到 746 帧（12.4333）。每段补齐一次，9 段累积后边界偏移最多 2 帧。动画相位差 0.03 s，eOut 曲线在起点斜率最大，所以单帧 PSNR 掉到 20 上下。

这是"强制帧对齐"的必然结果，不是错误。手写版那 30 条帧边界歧义（见 §三）就是同一个问题的另一面——**要么边界清晰但有亚帧位移，要么零位移但边界含糊**。选前者。

### 未做的

- **跨段引用**（`@scenes[2].end`）：需要拓扑排序与环检测，而真正需要跨段跳转时应该由各片的 `build.py` 从配音重建整条轴，不该在 params 里手写图。
- **captions 不会自动跟随 scenes**：它们是两条独立数组，各自解析自己的 `@prev`。真实使用中 captions 由 `build.py` 从配音时间生成，不走手写链。

## 十三、内容模型打通 paper（2026-11-14 深夜）

`tools/knowledge` 原先只产 science 骨架，但 `guide.json` 里 A 母版的 pairing 写的就是 `science / paper`，实际用起来 paper 更合适（science 的 18 个图标全是医学向）。中间那段映射是手写的——`content/birthday-paradox/build.py` 里 9 处 `scenes.append`，换片就得重抄。

现在 `buildSkeleton({ target: 'paper' })` 按母版表直接出 paper 的 `scenes`：

- `guide.json` 的 A（13 拍）、B（10 拍）加了 `paperType`；C–F 只有 flow，按 `scienceType` 兜底映射。
- 段长按 `≤7s` 拆（paper 镜头设计 4–7s，母版一拍 12–15s）。
- **gap 只加在拍之间**，子段之间不留——每段都加会让 12 拍拆成 32 段后凭空多 5 秒。

实测六母版 × 两档全部生成成功，17–32 段、105.5–167.8s、最长段 5.9–7.0s，全部过时间轴校验。

### 三个 bug

1. **`planBeats` 重构 beats 时丢了 `paperType`**，导致全部退到兜底映射（B03 该是 `number` 却变成 `steps`）。
2. **拆段给每个子段都加了 0.25s 的「拍间隔」**，12 拍拆 32 段后凭空多出 5 秒（167.75 → 172.75）。
3. **args 里的绝对时间没平移**——`paper` 的 `at` / `leftAt` / `cards[][1]` 是绝对秒，照抄 v8t 的值会让元素在新段开始时「早就出现过」，画面立刻静止。**freeze 16.7s → 5.3s** 全部靠这一处修（按 `新t0 − 原t0` 整体平移）。

### 骨架的静止是结构性的，不是 bug

修完时间平移后：A 母版 6.1s、C 母版 17.2s。差异来自**连续同类型段**——C 的段型是 `hero hero point point steps steps steps number number checklist×3 quote×2 compare×3 outro×2`，同拍拆出的子段用同一份占位 args，首尾相接就连成死画面。

试过两条路都不成立：

| 尝试 | 结果 |
|---|---|
| 给每段不同文案 | 17.2 → 16.7s，几乎无效 |
| 元素时间按段长缩放铺满 | A 5.3→6.1s **更差**，C 不变 |

根因：paper 每段的动画只在「元素逐个出现」，出现完就静止；同一份 args 复制两次，得到的就是两段一样的画面。**这件事骨架解决不了**——一拍必须拆成内容不同的两三个镜头，那是写稿的事。已写进骨架的 `_meta.freezeHint`。

## 十四、音频链路的两个坑（2026-11-14 深夜）

给知识片加转场音效时暴露的，且都影响通用混音。

### 1. `alimiter` 默认会把峰值抬回去

`src/audio-mix.mjs` 里原本是：

```
alimiter=limit=0.95
```

`alimiter` 的 `level` 参数默认 **true**（auto level）——它会把输出电平**自动拉回 limit**，等于没限幅。加音效后成片真峰值到 **0.2 dBTP**，AAC 编码的 inter-sample 过冲再叠一层，必然越线。

改成：

```
alimiter=limit=0.86:level=false
```

`level=false` 才是真的只削峰不抬电平；`limit=0.86`（≈ −1.3 dBFS）给 AAC 过冲留 1 dB 余量。改后 −16.8 → **−17.3 LUFS**（仍在 −16±2 内），真峰值合规。

### 2. earshot 音效的增益不能统一给

内置合成音（`impact` / `whoosh` / `tick`）是几条正弦加噪声，塑料感明显；换成 earshot 的 FORGE 配方后质感差一档：

| 用途 | 音效 | 时长 | 峰值 | gain |
|---|---|---|---|---|
| 开场 | `pro_impact/short` | 0.67 s | 0.181 | 0.34 |
| 拍间 | `swish/soft` | 0.88 s | 0.110 | 0.28 |
| 数字段 | `click/soft` | 0.09 s | 0.004 | 1.5 |

三条的峰值差 **40 倍**，用统一 gain 的结果是：impact 炸、click 听不见。必须按各自峰值单独给。

### 3. 顺手修的仓库卫生

`content/<片>/` 整个目录原先没有忽略规则——`audio/` 有 **42 MB**（配音 mp3 + 混音 wav），`params*.json` 每次出片都变。加了两条按身份特征匹配的规则：

```
content/*/params*.json
content/*/audio/
content/*/ocr.txt
```

入库只剩 `script.json` / `facts.md` / `build.*` / `bgm.*` / `mix.*` / `make.sh` / `README.md` 七个文件。

## 十五、批量入口与字幕回读（2026-11-14）

### `tools/render-all.mjs`

扫 `content/<片>/`，按状态决定重建还是只重渲：

| 状态 | 判据 | 动作 |
|---|---|---|
| `skeleton` | 只有 script.json | 跳过（脚手架刚建） |
| `stale` | script.json 比 params-chain.json 新 | 重渲前需 `make.sh` |
| `ready` | params + 混音都在且不旧 | 直接渲 |
| `done` | `out/<slug>.mp4` 比 params 新 | 跳过 |

默认只重渲（11.6s/支），`--rebuild` 才走 `make.sh`（重配音+重混音，几十秒）。出完统一过一次门禁。

产物命名统一到 `out/<slug>.mp4`——一支片一个成品，版本交给 git，不再有 `-v2/-v3/-v4` 后缀。

### `--caption-check`：字幕有没有真的显示出来

```bash
node src/gate.mjs out/film.mp4 --caption-check content/<slug>/params-abs.json
```

拿 `params.captions` 的文本，与该时刻 OCR 读到的**字幕区**（`y<0.3`）比对字符覆盖率，低于 60% 报一条。

**只报不拦**：OCR 对逐字擦除动画的首字常读不到（`一个班` 读成 `个班`），覆盖率天然打不满。它抓的是“整条字幕没出现 / 被裁掉大半”，不是逐字校对。

负向自检：把第 6 条字幕替换成不存在的文字 → 报 `字幕 1/39 条没读全（最低覆盖 11%）`；正常片 → 0 告警。

`--caption-check` 会把 OCR 抽帧自动加密到 1 秒（字幕条平均 2–3 秒，2 秒间隔会漏）。

## 十六、吸收 lemo-opuscar 的一条规则（2026-11-14）

上游 `lemomo-ai/lemo-opuscar`（15.7K★，99 种代码风格）的 `STYLE.md` 模板质量很高，值得学的是它的**结构纪律**：

> STYLE.md 只放「每支片都成立的规则」（6–11 KB，11 个固定小节）；
> 所有「这一支片的具体选择」——故事、分镜、BPM、调色板、时长——全部赶去 DEMO.md。
> 其中 §11「Variation space」反过来强制列出**每支片由 agent 决定的**：3 种结构 / 3 种开场 / 3 种结尾。

一句话：**风格是约束，不是模板**。

它的 §4 给了一条可直接执行的判据：字幕停留 `≥ max(1.8s, speech + 0.6s)`。

### 照搬会误报，按本仓校准

直接照搬，本仓 39 条字幕里 **22 条全报**。原因不是我们做得差，是判据和我们的做法冲突：

本仓字幕与配音同步，一条覆盖 N 字时说话时长就是 N/5.5，要求「停留 ≥ 说话 + 0.6」在数学上**永远不成立**（除非字幕重叠或提前出现）。lemo 那边字幕条通常跨多句，才有缓冲空间。

去掉 `+0.6` 后是 `≥ max(1.8s, 字数/5.5)`，实测报 **5/39 条**——这 5 条是真的太快（最短 1.23s）。

### 修生成逻辑

`fit_captions()`（`build.py` 与脚手架 `build.mjs` 都有）：

1. 按标点切到 ≤18 字；
2. 若各条所需时长之和超过这段的时长，**合并最短的相邻对**，直到放得下；
3. 按「所需时长」加权分配，**不按字数**——按字数分会让 6 字的短句只拿到 1.2s。

结果：39 → 38 条，**停留不足 5 → 0 条**，最短 1.83s，最长一条 19 字。

### 没做的

- 不搬 99 种风格：那是 99 份 CC BY-NC 文档（非商业限制），而且每种风格背后是各写一份 `film.js`，与本仓「7 支参数化版式」是两条路。
- 不搬 STYLE.md 的全文结构（11 小节写成一份要几小时/支），但把它当**模板**给 `kits/*/README.md` 未来重写时用。
- 代码是 MIT，真要用可以直接抄；但架构不同（它每次让 Claude 现写代码，我们是固定渲染器 + 参数），抄了也没用。
