| 00:12 | 服务命名为 `renderd`，包结构 `renderd/renderd/` | 与已有 `cutproof/`（验证脚手架）区分：一个是可验证性实验，一个是可运行服务 | 两套代码并存，`cutproof` 作为回归基线保留 |

| 00:12 | 队列用 SQLite `UPDATE … RETURNING` 做原子领取 + 租约，不用「先查后改」 | 多方并发下「先查后改」必然双领；`UPDATE … RETURNING` 单语句原子，且能带租约 | 崩溃恢复靠 `lease_until` 扫描，不依赖进程存活 |
| 00:12 | 时间量一律整数帧，IR 里不出现浮点秒 | 29.97/23.976 下浮点秒必然累积漂移；且跨引擎取整规则不同 | 接口层接收 `duration_frames` 而不是 `duration` |
| 00:12 | 文字层在编译期栅格化为 PNG，哈希进缓存键 | 让目标机现算字形会把输出绑定到那台机器的 freetype 版本，跨端一致从物理上不可保证 | 必须有 Pillow；无 Pillow 时含文字的模板直接拒绝编译（不静默降级） |
| 00:12 | MLT 分支保留但只做结构校验，不作为默认后端 | 本机无 melt 运行时，无法端到端验证；拿未验证的后端做默认是不负责的 | 默认后端 `ffmpeg`；MLT 作为可切换后端，接口一致 |
| 00:12 | 渲染缓存键 = sha256(规范化 IR + 后端 + 引擎版本 + 字体集哈希 + 输出规格) | 缓存命中的前提是「同样的输入产出同样的字节」，必须把引擎版本和字体都算进去 | 升级引擎或换字体自动失效，不会返回旧片 |

| 00:12 | 失败重试分两类：`transient`（超时/OOM/编码会话）自动重试，`permanent`（素材坏/IR 非法/字体缺）立即失败 | 对永久性错误重试只会烧算力并延迟客户拿到错误信息的时间 | 重试表在 `errors.py` 里，单一来源 |

| 00:12 | 证据回执（receipt）作为一等公民落盘并入库，而非仅返回 URL | Agent 看不见视频，只给 URL 会让它靠重试试探，烧的是算力配额 | 每次成功渲染都产出 receipt + 证据图，API 与 MCP 都可取 |
| 00:12 | 单进程多线程 worker，每个 job 起一个 ffmpeg 子进程；并发由 `WORKER_CONCURRENCY` 控制 | 渲染是子进程密集而非线程密集；ffmpeg 自己会吃满分配到的核 | 单机可跑；多机只需共享同一 SQLite 所在卷（或换 store 实现） |
| 00:12 | 输出交付默认写本地卷并返回带 HMAC 签名的下载 URL | 无人值守阶段不接对象存储；但交付契约（签名 URL）保持与生产一致 | 换 S3/OSS 只改 `delivery.py` 的 `put()` |
| 00:12 | 所有阶段写 `job_events` 表（stage/message/data） | 出问题要能回答「这条任务在第几阶段、因为什么、卡了多久」，日志文件做不到结构化查询 | 审计与排障都读这张表 |
| 00:12 | 端口默认 8787，数据目录默认 `renderd/var` | 避开常用端口；数据与代码同仓但被 .gitignore | 部署文档里写明可用 env 覆盖 |
| 00:12 | 不实现「自动清理旧产物」的定时任务，只提供 `renderd gc` 命令 | 删除是不可逆操作，无人值守期间不应自动执行 | 需人工或外部定时器调用 |

## 续轮 2 · 生产级异步（09:04 起）

| 时间 | 决策 | 理由 | 影响 |
|---|---|---|---|
| 09:04 | 背压检查放在 dry_run 之后、真正 INSERT 之前 | dry_run 只试算不占队列，不该被背压拦；但也不能在预检前拦（错误要给全） | 超限 `429 E_QUEUE_FULL`，retryable=true，客户端可退避重试 |
| 09:04 | 背压做两道：全局 depth + 租户 inflight | 只做全局挡不住「一个租户灌满、所有人排队」这个最常见事故形态 | `RENDERD_MAX_QUEUE_DEPTH=2000` / `RENDERD_MAX_TENANT_INFLIGHT=8` |
| 09:04 | 重试退避 `base × attempts²`（默认 1/4/9s），用 `available_at` 列 | 原来 fail 直接改回 accepted，worker 0.5s 轮询会让 NVENC/OOM 类瞬态错误几秒内连烧完 3 次 | claim 子查询过滤未到期任务；确定性失败不设退避直接进死信 |
| 09:04 | `recover_expired()` 重排时清空 `available_at` | 猝死回收应立即重试，不该再叠加退避延迟 | reaper 路径保持快速自愈（实测 attempts=2） |
| 09:04 | `replay` 就地改回 accepted、重置 attempts、清错误，不新建 job | 幂等键仍在；新建会让同一业务 key 出现两条计费记录 | DLQ 可对账可重放，且不破坏幂等语义 |
| 09:04 | **不在 SIGTERM 自动归还 running 任务** | 原进程可能还在跑 ffmpeg，改回 accepted 会被新 worker 立刻领走 → 双领，正确性事故比晚几十秒回收严重 | 改为 `STOPSIGNAL SIGTERM` + `stop_grace_period: 300s` 让当前任务跑完；reaper 只兜底真猝死 |
| 09:04 | `release` 做成手动 CLI 而非自动行为 | 只有运维确认进程已退出后才安全 | `renderd release --worker w1` 提前收回租约 |
| 09:04 | webhook 增加 `event_id = job_id:status:attempts` | at-least-once 投递下收端必须有稳定去重键 | 同次尝试重发同键；replay 后 attempts 重置生成新键；契约写进 API.md |
| 09:04 | 索引创建移进 `_migrate()` 补列之后 | 语料回归用存量库首次跑出 `no such column: available_at`；SCHEMA 的 CREATE INDEX 排在 ALTER TABLE 之前 | 三个存量数据目录复测可正常打开并加列 |
| 09:15 | fd 门禁从绝对阈值 20 改成「增量 < 10」 | 长跑 18 分钟的容器常驻 worker/reaper 线程本就有 20+ fd，绝对值会误报；实测再跑 10 条渲染 delta=0、60 次 HTTP 请求 delta=1，无持续泄漏 | 门禁测的是「有没有继续涨」，而不是「现在有几个」 |
| 09:15 | `render.run()` 的 pump 线程 join 后显式关 stdout/stderr 管道 | 只靠 Popen GC 会留下 TextIOWrapper 的 ResourceWarning 与悬挂 pipe fd | 每次渲染少 2 个悬挂 fd，消除告警噪音 |

## 续轮 3 · PG 双后端与异步架构复审（09:39–10:02）

| 时间 | 决策 | 理由 | 影响 |

## 续轮 9 · 编码分支与容器 tag（14:55–15:20）

起因：回答「后端引擎是否全部搞定」时去实跑 hevc/av1（此前只有 h264 走过回归），
结果发现两条**能出片但交付不出去**的问题。

| 时间 | 决策 | 理由 | 影响 |
|---|---|---|---|
| 14:58 | 三种编码都显式写 `-tag:v`（h264=avc1 / hevc=**hvc1** / av1=av01） | ffmpeg 默认把 HEVC 写成 `hev1`，而 Safari / QuickTime / iOS 只认 `hvc1`，拿到 hev1 直接不播。客户选 HEVC 通常就是为了 Apple 端省带宽 | 实测 tag 从 hev1 → hvc1；h264/av1 值不变但显式写，便于进指纹 |

### 为什么这不是「小问题」

`hev1` 与 `hvc1` 只差两字节，但语义不同：`hev1` 允许参数集（VPS/SPS/PPS）在码流中
重复出现，`hvc1` 要求参数集只在 `hvcC` 盒子里。Apple 的解复用器只实现后者。
所以「渲染成功 + 断言通过 + 回执 pass」的成片，在 iPhone 上打不开 —— 这是最容易
被自动化测试放过的一类缺陷：**技术指标全绿，交付目标不成立**。
