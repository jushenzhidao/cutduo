# 仓库深度整理 · 2026-11-15

> 目标：**agent API first / 方便后续蒸馏 / 方便扩展**，并对整理本身做对抗审查。
> 方法：先找「同一事实的多个副本」，再找「默认值掩盖的失败」，最后找「打包与运行时的依赖缺口」。

## 二、P0：diagram 没接 API

**证据（改动前）**

```text
kits/ 目录：clay collage desk diagram editorial iso mg paper science   （9 支）
capabilities ids：clay collage desk editorial iso mg night-card paper science（9 条）
                  ↑ 其中 night-card 是模板，不是 kit
⇒ 实际只覆盖 8 支 kit，diagram 缺失
```

`tools/smoke.sh` 的目录断言是「kits/ 里不许有目录没接 API」，所以这条在改动前**必然 FAIL**；
但人读 README 只会看到「七套版式」，不会发现少的是哪一支。

**根因**：`api/registry.mjs` 是手写 import + `MODULES` 数组。加 kit 要改两处，
而漏改的后果是「能力清单少一条」，没有任何运行时报错。

**修法**

1. `kits/diagram/render.mjs` 补 `--probe / --at / --audio / --fps / --crf / --preset`；
   并让 `params.timing` 也能提供字级时间戳（API 请求形状里没有 timing 字段）。
2. 新增 `api/kits/diagram.mjs`，声明 13 类段型、5 个 preset、单进程限制。
3. 注册表改为扫描 `api/kits/*.mjs`：
   - 文件名必须等于 `capability.id`，否则启动时抛错；
   - 缺 `capability` / `adapter` 也启动时抛错；
   - `_` 开头的文件跳过（`_runner.mjs`）。
4. `_runner.mjs` 增加 `supportedOverrides`：diagram 传 `workers` 会返回 `BAD_REQUEST`，
   不再静默忽略。
5. 冒烟的 API 探针循环改为遍历能力清单，不再手写 8 个 id（旧列表同时漏了 iso / diagram）。

**验证**

```text
capabilities: 10 条（9 kits + night-card）
api.probe：10/10 PASS
diagram API render：390 帧 / 26s / 15fps / 4.98s（fps 覆盖生效）
负向：capability.id 与文件名不一致 ⇒ 启动 exit 1
负向：diagram + workers=8 ⇒ BAD_REQUEST，fix 列出可用 overrides
```

## 三、P1：五套数字与「手抄清单」

| 位置 | 改动前 | 改动后 |
|---|---|---|
| `README.md` | 七套版式（表 7 行） | 九套版式（表 9 行） |
| `kits/README.md` | 八套版式 | 九套版式 |
| `api/capabilities.json` | 9 条（缺 diagram） | 10 条（9 kits + night-card） |
| `kits/STYLES.md` | 11 支，漏 iso / diagram | 13 支可渲染，补齐 |
| 真实可渲染 | 13 支（9 kits + 4 三件套模板） | 13 支 |

**修法不是「把数字改对」，而是取消手抄**：

1. `tools/inventory.mjs` 扫描 `kits/` 与 `templates/own/`，生成
   `docs/inventory.json`（机器）与 `docs/inventory.md`（人）。
   - `uid = kit:<id> / template:<id>`，解决 `editorial` 同名不同物；
   - `api` 字段只在「确实是同一支」时为真（night-card 是，DOM 版 editorial 不是）。
2. `tools/check-docs.mjs` 做 15 项检查：
   - inventory 是否过期；
   - kits/ 目录是否全部接 API；API 是否有孤儿能力；
   - 入口文件是否还存在；
   - README / kits/README / STYLES / inventory 是否覆盖每一支 kit；
   - 「N 套版式 / 共 N 支」的数字是否等于真实值；
   - 文档里的仓库路径、`npm run` 引用是否存在；
   - `tools/README.md` 是否登记了每个脚本；
   - 蒸馏索引是否过期。
3. `tools/smoke.sh` 末尾跑 `check-docs`，所以 `npm run check` 一条命令覆盖出帧 + 文档。

**负向验证**（都实测）

```text
把 README 的「九套」改成「八套」⇒ FAIL: README.md 数字漂移（应为 9）
临时加一个 id=zz-orphan 的 adapter ⇒ FAIL: 孤儿能力 / 入口不存在
```

## 四、P1：容器里 night-card 是「能列出、不能出片」

**证据**

- `api/kits/night-card.mjs` 在能力清单里，默认入口 `render.mjs --kit night-card`；
- `render.mjs` 的三件套宿主从 `templates/own/<id>/src` 加载；
- `.dockerignore` 排除了整个 `templates/`；
- `deploy/package.sh` 的 tar 清单也没有 `templates/`。

⇒ 容器里 `capabilities` / `validate` 都成功，只有真正出片时才报「找不到模板」。
这类错误最贵：health 正常、协议正常，故障发生在交付路径上。

**修法**

- `.dockerignore` 只排 `templates/fixtures`，保留 `templates/own`；
- `deploy/package.sh` 打包 `templates/own`，自检清单加
  `templates/own/night-card/src/kit.js`。

**未验证**：没有实跑 `docker build`（需要网络与 x86 构建），只做了路径存在性与 `bash -n` 检查。

## 五、P2：API 契约的三处「默认值掩盖」

1. **overrides 类型**：CLI 的 `--fps 15` 是字符串，JSON 调用方传数字；改动前回执里
   同一字段会出现 `"15"` 与 `15` 两种类型。现在 `api/contract.mjs` 统一转 number，
   并加范围：`fps 1–240 / workers 1–64 / crf 0–51 / at ≥0`；越界直接 `BAD_REQUEST`。
2. **不支持的超参被静默忽略**：diagram 传 `--workers`、editorial 传 `--fps/--workers/--crf/--preset`
   以前都会「接受但不起作用」。现在 adapter 用 `supportedOverrides` 拒绝，并在 `fix` 里列出可用项；
   desk / mg 也补了白名单（只收 `fps/workers/crf/preset`）。
3. **probe 的 at**：`api/index.mjs` 以前直接用 raw 请求里的字符串，现在用归一化后的数字；
   回执里的 `at` 从 `"3"` 变为 `3`。

## 六、P2：两个检查器自身的缺陷

| 位置 | 症状 | 修法 |
|---|---|---|
| `tools/inventory.mjs` | `templates/own/editorial` 与 `kits/editorial` 同名，按 id 查 capability 会把 DOM 版算成「已接 API」 | 只有「三件套」或 schema 在 `templates/own/` 下才算 API；`apiRegistered` 从 11 修正为 10 |
| `tools/distill-check.mjs` | 产物缺失时先 push 错误，后面仍 `fs.statSync` 缺失路径 ⇒ 整个检查崩掉 | 先 `existsSync` 再 `statSync`；负向用例已验证返回 exit 1 且报两条 |

  ├─ api/capabilities.json      代码生成：id / 画幅 / schema / presets / 入口
  ├─ docs/inventory.json        代码生成：13 支可渲染 / 10 支接 API（含模板）

  ├─ docs/蒸馏-索引.md           9 条登记（自动生成）
  └─ tools/README.md            73 个脚本的分组索引

**扩展一支版式的路径**（现在只有两步会碰人）：

```bash
# 1. 写渲染器 + adapter（文件名必须等于 id）
kits/<id>/  +  api/kits/<id>.mjs

# 2. 生成清单并全量检查
npm run inv && npm run check
```

漏接、漏文档、入口搬家都会在 `npm run check` 里 FAIL，不再依赖「记得改五处」。

## 八、对抗审查：这套整理自身还有什么问题

1. **`inventory.renderable` 是结构判断，不是运行判断**。它只看
   `kits/<id>` 是否存在、三件套是否齐全；真正的「能出片」由 smoke 的 10 个探针覆盖。
   `chalkboard` / `cute-mv` / `sketchnote` 三支模板不在 API，也不在 smoke 里，
   只有 `template-smoke` 能验——这是当前的覆盖空洞。
2. **文档数字检查只抓显式声明**。`N 套版式 / 共 N 支` 能抓；「三支各有独立入口」这类
   自然语言数量仍会漂移。策略是：能生成的清单不再手写，判断性文字不写数字。
3. **tools 索引按 basename 匹配**。两个不同子目录里的同名脚本会互相「顶替」；
   当前没有同名，属于可接受的弱检查。
4. **自动发现是「启动即失败」策略**。一个 adapter 写坏会让所有 `capabilities` 不可用。
   这是刻意的取舍：静默少一支比启动失败更难查。
5. **`check-kit-contract` 的 8/8 不是全部**。science 的 schema 在 `template/` 下、
   night-card 在 `templates/own/` 下，两者由 template-smoke / check-template 覆盖。
   已在输出里标口径，没有强行混进同一个段型提取器。
6. **`deploy/package.sh` 没有端到端跑**。它会把 `content/`（本地 543 MB，含音频与派生
   params）整包打进去；镜像体积可能远大于必要。建议下一步把 `content/*/audio` 与
   `content/*/params*.json` 排除，只留默认 preset。
7. **白名单只覆盖四支**。paper / science / clay / collage / iso / night-card 仍共用全局
   overrides 列表；其中 `theme` / `transition` 只有 paper 的渲染器真正消费，别的支可能忽略。
   下一步是把「支持哪些超参」写进 capability 并由 `buildArgs` 统一裁剪，而不是每支各写一遍。
8. **`deliverables/` 没有物理搬家**。里面 21 MB 是验收证据，删了无法回溯；
   `packages/` 是构建产物、已被 gitignore。按「路径稳定性优先于整齐」只加了
   `deliverables/README.md` 说明边界，不做批量移动。
