# hypit 蒸馏评估（2026-11-14）

> 对象：`hypit-ai/hypit`（29,669★ / 3,463 fork / TypeScript / 63 MB）
> 判据：本项目「半蒸馏」标准 —— 上游是**版式枚举**还是**机制参数**；换宿主能否讲新内容。

## 一、结论

1. **它不是渲染器，是"视频的作者语言 + 编译器 + 运行时 + Provider 生态"。** 核心是 SVML（XML-like 标记）→ compiler → 不可变图 → runtime 执行；渲染走 64 个 headless Chromium 并发，与本仓 Skia 直出属不同路线。
2. **协议不允许拷代码。** 修改版 Apache 2.0 明确禁止多租户 SaaS 与商业再分发，且 fork 必须以同协议发布。cutduo 若将来对外提供服务，把它的代码搬进来会让整个仓库变成该协议的衍生品。**只能学架构，自己重写。**
3. **真正值得蒸的只有一条：时间模型的四层分离。** 其余（compiler 分层、provider 生态、词级 DP 对齐）对本仓是过度设计或不可用。

**核心主张**（README 原话）：*"all anchored to words instead of seconds"* —— 视频工作流锚定到**词**而不是**秒**。

## 三、协议：能用什么、不能用什么

| 条款 | 内容 | 对 cutduo 的含义 |
|---|---|---|
| 允许 | 自用、组织内商用、为客户做项目、单租户部署 | 内部出片、给客户交付成片：**可以** |
| 禁止 a | 多租户服务（一个 tenant = 一个 workspace；两个外部主体各持 workspace 即构成多租户） | **如果 cutduo 的 API/MCP 对外开放给多个用户，就是多租户** |
| 禁止 b | 商业再分发（售卖、收费提供、打包进产品给第三方） | 不能把 hypit 或其衍生品当产品卖 |
| 允许 | fork / 修改 / 发布源码，但**必须以同一协议发布**且不用于商业获利 | 抄了代码，cutduo 就得换成这个协议 |
| 禁止 c | 移除 CLI / 报告 / manifest 里的 LOGO 与版权 | — |
| 归属 | **输出内容完全归使用者**，包括商用 | 出的片是你的，这条没问题 |

**结论**：思想与架构不受版权保护，可以学；**代码一行都不要拷**。

## 五、精华清单

### 1. 四层时间模型（唯一优先项）

上游把"时间"拆成四层，每层只做一件事：

```
Narrative（语义）      Moment / Selection / Segment —— "哪句话""哪个论点"
   ↓ Alignment          把语义边界定位到某个 LocalTemporalDomain（如音频的 [0.5,2.3]s）
Projection              (Alignment + Domain + Window) → Timeline 上的绝对位置
   ↓
TemporalInstant / TemporalWindow    通用组件只消费这两个，不知道语义来源
```

三条关键约束（`temporal/README`）：

- `TemporalWindow` 是**半开区间** `[start, end)`，且必须非空；`TemporalInstant` 是**帧边界**。
- 校验严格：拒绝窗口端点不在同一 Timeline、拒绝倒序/空窗口、拒绝非精确的局部域投影、拒绝不兼容帧率。**不裁剪、不修复、不推断**。
- `TemporalExtent`（无位置的帧数）让"导入/生成的结果"决定时间线长度，而时间线不需要懂媒体或语音。

**为什么这条值得蒸**：本仓现在是"绝对秒"。生日悖论那支片里，我是用 `build.py` 从配音实测时长**反推**时间轴的——这已经是半个 Projection，但它是脚本里的一次性逻辑，不是可复用的契约。上游把它变成了**类型**：画面元素声明 `during={proof}`，改文案后重新编译，时间自动重算。

**落点建议**：`src/timing.mjs` 引入 `Instant`/`Window` 两个类型与校验（半开区间、帧边界、同 Timeline），`kits/*/params` 的时间字段统一走它。成本 1 天，收益是"改文案不用手改时间段"。

### 2. 编辑语义：改声明，不改消费方

`temporal/EDITING.md` 给了一张表，规定**改哪一端就动哪个字段**：

| 作者写法 | 移动 | 改前缘 | 改后缘 |
|---|---|---|---|
| `from="2s" for="8f"` | 改 `from`，保留 `for` | `from` 与 `for` **原子**重写，让末端不动 | 只改 `for` |
| `until="3s" for="8f"` | 改 `until`，保留 `for` | 只改 `for` | `until` 与 `for` 原子重写，让起点不动 |
| `from="1s" until="3s"` | 两个都平移 | 改 `from` | 改 `until` |

核心原则：**时间值归它的生产者所有，消费方没有反向推断权**。上游明确拒绝"自动求逆、隐藏兼容回退、中心化时间血缘注册表"。

**为什么值得蒸**：它精确回答了"用户拖一下时间轴，该改哪个字段"这个问题。本仓目前的答案是"改 params 里的数字"——没有原子性保证，改 `t0` 不改 `t1` 就会让时长漂移。

### 3. 证据 ≠ 语义真理

`speech-evidence` 的设计：证据包携带的是「观察」（词、字、分数、语音活动区间，16 kHz 精确采样坐标），不是「作者想说什么」。三条纪律：

- 缺词时间**就留空**，不臆造成静音；
- 词区间半开且**保留重叠**，不猜作者指哪一次出现；
- 证据在**它自己的局部时钟**上，直到显式投影才上 Timeline。

对 cutduo 的用处：`facts.md` 台账、OCR 回读、字幕对齐三者的关系可以照这个划清——OCR 是"观察"，台账是"语义"，不能让 OCR 反过来定义台账。

## 六、对抗审查

1. **"锚定到词"在本仓是过度设计。** 上游用 WhisperX + 有界单调 M:N 动态规划做词级对齐，处理"脚本与语音不一致"（漏读、插入、改写）。本仓实测 `edge-tts` 只给整段时间戳，没有词级边界；要上词级就得引几 GB 的 ASR 模型。而按字符比例分配的误差在 100–300 ms，知识片上看不出来。**除非要做逐字卡拉OK字幕，否则不划算。**
2. **架构文档的抽象度是学习成本，不是先进性。** 例如「Temporal does not carry a closed source-kind union or a domain projector」「It is not an ownership lock on consumers」——这些句子在保护一个多产品共用的核心，对单产品读者是噪音。
3. **29.7k stars 但 API 未冻结。** 0.3 → 0.3.1 都有迁移指南，说明还在改接口。当参考读，别当依赖跟。
4. **它是 SaaS 公司的开源核心。** 设计目标是"多租户 + 生态 + 组件市场"，与本仓"单机 ≤12 s 出片"的目标函数不同。它的 64 进程 Chromium 并发与本仓 15 worker Skia 是两条路，不能混。
5. **协议是实质约束，不只是形式。** 若 cutduo 的 MCP/API 将来对外，只要代码里有 hypit 的衍生物，就落入多租户条款。这条必须在动代码之前讲清楚。

## 七、建议

| 步 | 动作 | 判据 | 成本 |
|---|---|---|---|
| 1 | `src/timing.mjs` 引入 `Instant`/`Window`（半开区间 + 帧边界 + 同 Timeline 校验） | 现有 params 全量过校验；非法窗口被拒 | 半天 |
| 2 | `kits/*/params` 的时间字段改走该类型，支持 `from/until/for` 三种声明 | 改一处时间不需要动相邻字段 | 1 天 |
| 3 | 把「证据 / 语义 / 输出」三类数据的边界写进 `docs/API.md` | OCR、台账、字幕各自的权威范围明确 | 半天 |
| — | 组件解剖 8 角色 | 等有第二个团队共写 kit 时再规范 | 暂缓 |

**不建议做**：搬 compiler 分层、接 Provider 生态、上 WhisperX 词级对齐。前两个是别人的产品形态，第三个在本仓投入产出比不成立。
